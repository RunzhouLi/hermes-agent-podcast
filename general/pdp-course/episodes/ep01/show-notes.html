# EP01 — 数据在哪里，工作就该怎样分？

这份学习附录配合本集双人播客使用。主线是同一份温度数据的旅程：**模拟生成网格 → 分析提出问题 → 模型学习关系或协助模拟**。这不是要求所有模型都只读取统计摘要；下游若需要空间结构，就必须保留相应信息。

需要的先备知识：认识数组、会加法和平均数。不要求先会并行 API。温度规则、机器配置、运行时间及四道练习均为教学自编例子，不是硬件实测、真实材料模型或官方考试题。

## 术语速查

| 中文／英文 | 本集使用的含义与必要边界 |
|---|---|
| 节点 node；集群 cluster | 节点是参与计算的一台机器；多个节点经网络协作。节点数不是核心数。 |
| 插槽 socket；核心 core | 本例一颗处理器占一个插槽，一颗处理器含多个物理核心。硬件线程和 GPU 执行单元不能不加区分地计作同一种核心。 |
| 进程 process；线程 thread | 进程有各自地址空间；同一进程的线程共享地址空间。多个进程即便同处一个节点，也不自动共享全部对象。 |
| 共享内存 shared memory | 多个执行者可访问共同数据；不承诺无竞争或访问等速。 |
| UMA；NUMA | 较均匀的主存访问架构，与非统一内存访问架构的对照。NUMA 中数据与执行者的位置会改变访问路径。 |
| 缓存 cache；缓存一致性 cache coherence | 缓存靠近核心保存数据副本；coherence 协调缓存副本，不替代程序级同步，也不使复合读改写自动原子化。 |
| 数据局部性 data locality | 让计算靠近需要的数据，或减少不必要的往返；既可以讨论节点内，也可以讨论整个工作流。 |
| 消息传递 message passing；MPI | 分别持有数据的进程交换信息；MPI 是后续学习的接口，不是网络不存在的保证。 |
| BSP；超步 superstep；屏障 barrier | 批同步并行按超步组织计算、通信、同步。BSP 的语义不能简化为“任何 barrier 都会替我完成所有通信”。 |
| 混合并行 hybrid programming | 在适当层级组合模型，例如节点间消息传递、节点内线程；增加层数不等于增加收益。 |
| GPU；计算卸载 offloading | GPU 是候选计算设备；卸载包括安排计算和数据供给，必须检查端到端成本。 |
| split／map／shuffle／reduce | 分片、局部映射、按键重分布分组、按组归约；shuffle 可能跨网络。 |
| RDD | Resilient Distributed Dataset，弹性分布式数据集；分片、复用、恢复是其用途，不是一个自动永久驻留的共享数组。 |
| AI／ML／DL | 人工智能包含机器学习；深度学习属于机器学习。数据类型不是三者之间的绝对分界。 |
| training／evaluation／inference | 训练调整参数；评估检查固定模型的表现；推理用模型对输入产生预测。评估常调用推理，但目的不同。 |
| 数据泄漏 data leakage | 评估信息经预处理、训练或模型选择等路径影响拟合，使本应独立的检查不再独立。 |
| 原位分析 in situ analysis | 在模拟侧利用仍可用的数据做分析，减少落盘与远搬；分析、内存和归约仍有成本。 |
| 代理模型 surrogate model | 在验证范围内近似模拟的某些部分，或用于引导；不是取消误差检查的通行证。 |
| HPC；I/O | 高性能计算；输入输出。存储、网络、主存与设备之间的数据路径要一起考虑。 |

术语依据：来源 S01 物理页 5–7、10–15；来源 S02 物理页 4–6、11、13–14、17、20–22；《C01-K01 集群、节点、核心与内存层级》《C01-K02 并行编程模型与混合并行》《C01-K05 HPC、数据分析与 AI 的融合及数据局部性》。进程、线程和语言级同步的深入讨论去 EP03、EP05。

### 第一题：换一张机器地图

3. 工作再移到乙节点，只带甲进程里的普通指针就够吗？

### 第二题：换一轮数据试试

教学规则：新温度等于上一轮左邻、自己、右邻三个值的平均。第七轮三个旧值依次是 **12、24、54**。左邻和中心属于甲节点，右邻属于乙节点；甲已备齐全部第七轮输入。乙已算出右邻第八轮为 **36**，有人提议用它立刻覆盖旧边界。

1. 中心第八轮应该使用哪些值，得到多少？
2. 在本例 BSP 组织中，甲自己发完了消息，就能开始第九轮吗？
3. 把两块搬到同一节点，缓存一致性就能代替全部同步吗？

### 第三题：为一个分析任务选路

记录已经分散在多个节点。研究者反复改变高温阈值，每轮都按地区统计条数。

- 单 GPU 方案每轮：集中输入 6 秒，设备计算 2 秒，结果返回 1 秒。
- 现有 CPU 路径：端到端 8 秒。
- 假设三段顺序执行、不重叠，也没有遗漏的开销。

先比较给定方案。再提出另一种候选，说明本地能做什么、按什么键汇合、哪份数据值得复用，以及还需要哪些证据才能宣布更快。[需要提示](#h3)；[准备好再看答案](#a3)。

<a id="q4"></a>
### 第四题：最后一段数据要不要留下

模拟产生 240 GB，链路持续带宽为 8 GB/s。

- 原方案：全部传走，再分析 4 秒。
- 候选方案：原位处理 4 秒生成 8 GB 摘要，只传摘要。
- 两条路径均顺序执行、无重叠，暂不计其他开销。

摘要只有各块温度和与计数。各块格子数不同，每个格子权重相同。研究者既要全局均值，也要知道哪些高温格子连成一片。

计算两条路径时间；说明怎样由摘要合成全局均值，能否直接平均各块均值。再判断是否接受候选。若要补信息，原时间结论还能照搬吗？[需要提示](#h4)；[准备好再看答案](#a4)。

## 答案与判断依据

<a id="a1"></a>
### 第一题解析

- 每节点 `2 × 6 = 12` 核，集群 `3 × 12 = 36` 核。
- 同节点迁移可能把本地内存访问变成远端 NUMA 访问。题设明确物理页未迁移；地址仍可用不是等速证据，也不足以计算慢了几倍。
- 跨节点需要消息传递、远程访问等有明确语义的机制；本进程普通指针不是另一节点对象的通用访问方案。
- **常见错答：**只答 36，却声称“共享，所以同速”；或把所有核心当成独立节点。
- **判断标准：**层级计数、NUMA 成本、跨节点边界三项都解释到。不会哪项就回听 S02–S03。[返回导航](#q1)。

<a id="a2"></a>
### 第二题解析

- 使用第七轮：`(12 + 24 + 54) / 3 = 30`。混入第八轮右邻则为 `(12 + 24 + 36) / 3 = 24`，改变了算法。
- 旧数组供本轮读取，新数组接收本轮结果。新边界供下一轮使用；第一轮所需初始边界也必须提前准备。
- 自己发完不证明下一轮所需数据全齐，也不证明 BSP 超步交接条件成立。不能用任意 API 名叫 barrier 就推断通信完成。
- 同节点不消除读写依赖。coherence 不提供整段程序的同步或复合更新的原子性；没有依赖的任务也不必被强制套入全局屏障。
- **常见错答：**选“最新”值；只等自己；以硬件一致性代替程序规则。
- **判断标准：**正确时间层、继续条件、coherence 边界均解释到。算对数字但时间层理由错，仍需回听 S07–S08。
- S03 的“双方读零、写一”用于说明复合操作的逻辑风险，不是声称任何实际语言的无同步共享变量程序都只有这一种合法结果。C++ 数据竞争与语言规则在 EP03、EP05 专门区分。[回题目](#q2)。

<a id="a3"></a>
### 第三题解析

- 给定 GPU 路径 `6 + 2 + 1 = 9` 秒，慢于 8 秒。2 秒只是设备计算段。
- 本地清洗、筛选；每条高温记录贡献“地区、1”；相同地区的局部贡献需要汇合，必要时跨网络。这是 MapReduce 式数据组织，不要求再部署一套独立 MapReduce 系统；Spark 也能表达按键聚合。
- 多个阈值查询共同需要的是清洗后、尚未按某个阈值删掉的输入，而不只是某次筛选结果。Spark/RDD 的缓存复用是候选。
- 验证容量、重复次数、调度、通信和恢复等成本后，才有性能结论。若改为让 GPU 数据驻留，应重新计算，不再机械套用本题每轮 9 秒。
- **常见错答：**只比较 2 与 8；缓存最高阈值筛完的数据，却想支持更低阈值；以“用了 Spark”作为更快的证据。
- **判断标准：**完整计时、分组键、可复用输入、候选与已证结论的区别四项都说明。[回题目](#q3)。

<a id="a4"></a>
### 第四题解析

- 原路径：`240 / 8 = 30` 秒传输，加 4 秒分析，合计 **34 秒**。
- 候选路径：4 秒原位处理，加 `8 / 8 = 1` 秒传输，合计 **5 秒**。
- 全局等权均值是 `Σ各块温度和 / Σ各块计数`。各块格子数不同，直接平均各块均值会给块而不是格子相同权重，不能保证正确。
- 这不是等任务加速的证明。和与计数足够求上述均值，却不能恢复高温格子坐标和连通关系。
- 需要保留热点位置及连通判断所需的空间信息，包含跨块边界；也可根据需求保留原数据或检查点。具体摘要要由明确的下游问题决定，不能保证任何一份有限摘要适配未知的所有分析。
- 补充信息后，摘要大小、生成时间和后续处理都可能改变，5 秒必须重算。原题排除了不正确候选，尚未求得最优方案。
- **常见错答：**“5 秒更快，所以接受”；直接平均不等分块均值；或认为多个均值能恢复局部空间结构。
- **判断标准：**正确时间、按格子权重合并均值、摘要缺失信息、修复后重新记账四项都做到。[回题目](#q4)。

## 正文算例复盘

全部数字均为理想化教学输入；不要作为设备基准或现实模拟精度使用。GB 与 GB/s 使用同一计量约定。

| 场景 | 输入与推理 | 正确结论 |
|---|---|---|
| 层级计数 S02 | 2 节点 × 2 处理器 × 4 核 | 16 核，不是 16 节点 |
| 时间层 S07 | 旧值 20、30、40；误用右邻新值 70 | 正确 30；混层变 40 |
| GPU S12 | CPU 20 秒；传入 4、计算 3、传出 5，无重叠 | GPU 完整路径 12 秒 |
| 按键计数 S13 | 甲片北南北；乙片南北 | 北 3、南 2 |
| 平均的平均 S13 | 甲只有 10；乙有 30、30、30 | 平均均值误得 20；合并和 100、计数 4，正确 25 |
| 复用 S14 | 两条记录 28、36；严格大于阈值 30 或 25 | 分别 1 条、2 条；前一结果不能恢复后一所需记录 |
| 直线模型 S18–S19 | 预设直线族，训练点 (1,12)、(2,14) | 斜率 2、截距 10；输入 3 预测 16；若参考是 20，绝对差 4 |
| 链路 S21 | 600 GB 与 6 GB，经 10 GB/s 链路 | 60 秒与 0.6 秒，仅该链路传输时间 |
| 信息丢失 S21 | 20、40 与 30、30 | 均值同为 30，峰值与局部状态不同 |

等权平均的可合并摘要是 `(sum, count)`：先分别累加各片的和与数量，再相除。若网格体积不同而问题要体积平均，则需合并 `Σ(体积 × 温度)` 与 `Σ体积`，不能直接用记录数替代体积。此处还未展开浮点求和顺序与舍入误差。

### D4 — 学习流程、指标与工具清单

**本集保留在音频里的边界：**先确定数据角色，再拟合学习型预处理；验证集用于选择方案；最终测试集不参与拟合或选模。S19 的两点直线只是展示“从样本确定参数”，没有证明数据够用或规律就是直线。

来源 S02 物理页 20 还区分面向特定任务的狭义 AI 与设想中具有广泛能力的通用 AI。一个温度预测任务不能据此被称为通用智能。源页同时列举跨学科领域与常见数据形态；这些只作概念背景，不作为本集的分类背诵题。

来源 S02 物理页 21 的细项集中在这里，供检索，不要求本集会实现：

| 阶段 | 课件列项 | 阅读时不要混淆 |
|---|---|---|
| 原始输入 | 表格/矩阵、时间序列、图像、文本 | 数据形式不自动决定必须使用哪类模型 |
| 预处理 | 清洗、合理性检查、特征工程、转换、标准化/归一化、降维 | 并非每项都必须做；需要从样本学习参数的步骤须隔离拟合数据 |
| 训练 | 模型、优化器、损失函数、超参数 | 这是一组需要展开的职责，不是一条口令 |
| 分类评价 | accuracy、precision、F1 | 指标对应不同问题，不能只追一个高分忽略使用代价 |
| 回归评价 | mean squared error、R² | 预测连续温度属于回归；正文只用单点绝对偏差作直观示例，不把它当完整评估 |
| 验证设计 | 多折交叉验证 | 每折中的学习型预处理也只能从该折训练部分拟合 |
| 使用 | 对新样本进行 inference | 已有参数用于预测，不是默认继续训练 |

预处理隔离的补充依据：scikit-learn《Common pitfalls and recommended practices》“Data leakage”部分，明确区分先划分、训练侧拟合、两侧使用同一变换。

**EP36 的明确任务：**从 Tensor 与预测开始，逐步走过损失、梯度、反向传播、清梯度与优化器更新，再区分评估模式与梯度记录。求梯度不是已经更新参数，清梯度不是清空权重；这些要靠一次完整推演学习，不在本集塞成一小段术语。

来源 S02 物理页 22 的 PyTorch 清单保留为课程背景：Python/C++ 前端、`nn` 网络层、手工训练与评估循环、性能调优、分布式训练；配套库名 `torchaudio`、`torchtext`、`torchvision`。源页把 `2.3.1` 标为 “Latest stable version”，本附录不据此判断当前版本或支持状态，也不提供安装推荐。训练数据与 I/O 去 **EP37**；分布式训练去 **EP38**；性能测量与优化去 **EP39**。

### D5 — 融合生态、存储与精度比较

- 来源 S01 物理页 9–11 以 2015 年倡议及沙漏愿景引出融合。沙漏的“窄腰”是共同的数据管理、资源调度和通信服务：上接模拟/分析/学习，下接不同硬件；它是解耦思路，不是任何程序都自动最优的保证。
- 来源 S01 物理页 12–13 提及容器和编排：Docker、Singularity/Apptainer、Kubernetes；也提及 HBM 与互连 GPU。容器帮助组织软件依赖，不自动消除数据移动、驱动限制或算法问题。源页的普遍部署与规模措辞不作为所有 HPC 系统的现状照读。
- 来源 S01 物理页 14 的 FP64、FP16/FP8，以及模拟、分析、学习对照，是简化倾向。不是所有模拟都只用 FP64，也不是所有学习都能接受低精度；模拟参考结果本身也有误差。精度选择去 **EP13、EP39**。
- 来源 S01 物理页 15 的本地 SSD、非易失性内存、网络并行存储，是位置与介质的不同选择，不是一张普适速度排行。I/O 组织与布局去 **EP25–EP26**，训练暂存和供给去 **EP37**。
- 原位分析与 surrogate 的核心判断保留在本集：前者改变处理位置，后者近似部分计算；两者都需把开销、信息完整性和准确性纳入同一个工作流。
