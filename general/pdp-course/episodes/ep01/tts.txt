A: 我要做一个温度模拟，算完再分析哪里容易过热。我打算把机器尽量加满，模拟就会快，分析也会跟着快吧？
B: 先别决定买什么。假如模拟结束，数据还要全部写盘，再搬到另一套机器分析，你加的核心在搬数据时能做什么？
A: 可能都在等。我刚才只想了谁来算，没想算的东西在哪里。不过我可以把模拟和分析放到同一台机器，问题就解决了？
B: 这能减少一段路，但同一台机器里面也有远近。本集用一个自编的温度模拟—分析工作流，把这条路走完整：先找到数据，再分配工作，最后看模拟、统计和学习怎样协作。
A: 那我不先背框架名了。我想最后能解释：为什么这里用线程，那里要通信，什么时候才值得请 GPU 帮忙。
B: 这就是本集的目标。它是并行与以数据为中心的编程课程基础章的第一讲，覆盖集群层级、编程模型导航和融合工作流；不需要先听独立的零基础章。下一讲才定量追问：分出去以后，究竟能快多少。
A: 我平时说一台电脑有很多核。到了集群，是不是把这些核摊平，按编号分温度网格就行？
B: 先试着从外往里找。集群，英文 cluster，是通过网络连接起来的一组计算节点。节点，node，可以先理解为集群里的一台计算机。节点里面还有处理器插槽，socket；装在其中的多核处理器，又含多个计算核心，core。
A: 所以一个核心不是一个节点。先分给哪台机器，再分给机器里的哪个处理器，最后才落到哪个核。这些边界会改变拿数据的方式？
B: 会。节点内部可以有共享的物理地址空间，这叫共享内存，shared memory。多个执行者能够访问同一份内存中的对象；跨节点通常各有各的内存，不能把本进程里的普通指针直接当作另一节点对象的地址。
A: 那节点里面就公平了吧？既然大家都能访问温度数组，谁处理哪一块应该差不多。
B: 能访问，不等于访问代价相同。先想一种扁平设计：处理器访问主存的代价相对均匀，课件称它为 UMA，统一内存架构，Uniform Memory Architecture。与之对照的是 NUMA，非统一内存架构，Non-Uniform Memory Architecture：内存可能连在不同插槽附近，本地与远端访问的路不一样长。
A: 我试着改任务分法：让某个线程处理靠近它的温度数组。如果线程后来跑到另一插槽，数组下标虽然没变，它到数据的距离却变了。
B: 这就是数据局部性，data locality，在节点内的第一层含义。缓存，cache，又把常用数据放在更靠近核心的位置。课件画了一级、二级、三级缓存，再到内存接口和主存；具体共享方式不是每台机器都完全一样，但“离核心越近与容量有限之间存在取舍”这条地图要记住。
A: 课件还写了缓存一致性。如果硬件帮大家保持一致，那两个线程一起修改同一个统计量，就不用管了？
B: 这里要拆开两件事。缓存一致性，cache coherence，处理多个缓存副本的一致性问题；它不替你保证整段程序的同步，也不自动让“读出、修改、写回”成为不可分割的一步。两个线程可能都基于旧值更新，仍然需要合适的同步或任务拆分。
A: 所以 ccNUMA 里的 cc 是 cache coherent，缓存一致；它没有承诺“我怎么并发写都正确”。我可以先让每个线程算自己的局部统计，再用有协调的方式合并，而不是随便抢写。
B: 还要把视线拉回节点之外：网络把多个节点接起来，形成“节点内共享、节点间分布”的层级。课件在架构示意里也把 GPU 看作一种可纳入计算层级的单元，但不意味着 GPU 与 CPU 插槽的内存访问细节相同。
A: 那温度模拟的地图不是一排平等的核，而是核在插槽里，插槽在节点里，节点经网络组成集群。要分网格，先画边界和数据位置，再问怎么协调。
A: 层级这么麻烦，不如只用一个特别快的核心，省掉所有协调。我猜只要频率继续提高就行？
B: 你的方案确实省了并行协调，但功耗和散热会来约束它。课件用历史趋势说明，约二〇〇五年以后，单核性能增长放缓，频率受到功率和冷却限制，于是总计算能力越来越依靠更多核心。
A: 多一个核心不是也要多耗电吗？怎么会成为解决功耗的方向？
B: 关键不是“原样复制高速核心”，而是能效取舍。多核处理器把两个或更多独立计算核心集成在一个芯片上。课件的示意是：降低电压与频率，单核性能有所让步，但功耗下降更明显，于是可能在近似的功耗预算里，让多个较慢的核心合起来完成更多工作。
A: 我漏了“降一点单核速度，换取整体吞吐”这一步。不过它要成立，温度计算就得真能分给多个核，否则只是多了闲着的人。
B: 对，这张历史示意图解释动机，不是当前处理器的精确承诺。同样，加速器追求的是某些计算上的每瓦性能。课件列过 GPU、FPGA 和历史上的 MIC 等路线，不能把旧榜单份额当成今天的市场现状。
A: 那我现在有两份约束了：数据不能乱搬，功耗也不能无限加。接下来要找的是适合数据和硬件的分工方式，而不是单纯增加数量。
A: 我让每个节点负责一片温度网格，节点内再让线程分行处理。各算各的，不通信，应该最省事。
B: 对互不依赖的任务，这样很好。但我们的自编模拟规定：下一轮某个格子的温度，需要本轮邻居的信息。如果邻居恰好归另一节点呢？
A: 我得要对方的边界数据。那不能只按工作量平分，还得安排一轮结束后的交接。
B: 这就区分出两种表达。共享内存模型让线程通过共同地址空间访问数据，难点包括协调读写。消息传递，message passing，让拥有各自数据的进程显式发送和接收需要交换的内容；MPI 是后面会学到的消息传递接口。
A: 我原来以为它们只是不同写法，现在听来，它们首先在回答“谁拥有数据，谁能直接访问”。但发送完就能马上进入下一轮吗？
B: 一种组织方法叫批同步并行，Bulk-Synchronous Parallel，简称 BSP。执行分成一轮轮超步：本地计算、通信交换、同步屏障，barrier。开始这一步时，先保证上一步需要的邻居数据已可用；算出的新边界会在这一步交换，供下一步使用。
A: 那我用同一轮的旧值更新自己负责的整块网格，包括边界格，再把新边界发出去。是不是我发送完，就能抢先开始下一步？
B: 还不够。在这个 BSP 模型里，要等本超步所需通信完成、所有参与者到达同步点，再进入下一步；不能只根据自己已经发送就认为邻居数据已齐。
A: 我得分别检查两件事：用对时间层的数据更新整块，再等下一步依赖的数据就绪。温度计算需要邻居信息，BSP 是组织这种依赖的一种办法，不是所有并行程序都必须照着全球等待。
B: 在这种 BSP 组织里，快的参与者可能等慢的。BSP 给程序一个有结构的组织方法，也带来同步代价。课件指出，MapReduce、Pregel、Hama 等也借鉴了这样的阶段化设计思想，但不是说这些系统的每个细节都等同于同一个 BSP 实现。
A: 如果节点间消息传递，节点内线程共享内存，岂不是同一程序用了两种模型？我刚才还想选一个万能答案。
B: 这叫混合并行，hybrid programming，按层级混合不同范式。复杂节点里还可能有 GPU，于是局部计算又能交给加速器。我们不是为集齐技术，而是让每层承担它适合的工作。
A: 我能想到它扩大机会：以前只能把不同网格块分出去，现在块里面也能并行。但如果每层都说快一点，最后就能把加速倍数相乘吗？
B: 不能。新增层次可能覆盖原先没有并行化的工作，也可能增加传输、同步和资源竞争。课件的混合加速图应读作“存在额外并行机会”，不是乘法保证。到底受剩余串行部分怎样限制，留给下一讲的性能定律。
A: 回到温度模拟，我先确定边界依赖，再选择节点间怎么交换、节点内怎么分工。混合是对层级的回应，屏障是对依赖的回应，两者都不是越多越好。
A: 那我把温度模拟整段搬到 GPU。它有那么多计算单元，总该胜过 CPU 吧？
B: 你选中了并行资源，但还没看工作形状。课件的对比是：CPU 偏向低延迟，GPU 偏向大量相似工作的高吞吐。单个任务尽快结束，和很多任务单位时间完成得多，不是同一个优化目标。
A: 我可以把大量格子上重复的局部运算挑出来。但每一步都有分支、又只剩少量格子的部分，未必能把它用满。
B: 还要看内存层级和执行模型。图形处理器，Graphics Processing Unit，缩写 GPU，在这里用于通用计算。计算卸载，offloading，是把选定计算区域交给加速器，并安排它需要的数据到达那里、结果被后续步骤使用。
A: 所以不能只计 GPU 算的时间，假如温度数组来回传输更久，账面上的快就没意义。我能不能让连续几步都使用留在设备上的数据？
B: 这是值得评估的候选方案，要看依赖、容量和后续用途。CUDA 是课件展示的 GPU 编程路线之一；模型和库的具体 API 后面再讲。本集先学会判断是否有足够并行工作，以及收益能否抵过数据移动。
A: 我们停一下理地图：温度数据先落到节点和内存层级，任务按依赖分开，必要时通信和等待，规则而密集的局部计算再考虑 GPU。现在模拟结果出来了，分析阶段是不是还得重新判断？
B: 正因为分析的问题形状可能变了，我们不能把模拟的分工原样照搬。下一步从“更新邻居网格”，变成“按地区汇总记录”。
A: 结果很大，我让各节点先算平均值，再把这些平均值平均一下，应该就能得到全局平均温度？
B: 如果每个节点的记录数不同，你会给小分片和大分片同样的权重。先换一个更小的自编任务：按地区统计高温记录的条数。你会把哪些信息从每条记录里提出来？
A: 地区，以及这条是否高温。如果我们已经筛出了高温记录，那每条都贡献一。我先在本地做，最后按地区合并，不必集中全部原始记录。
B: 这就走到 MapReduce 的抽象了。数据大到单机或小集群内存装不下时，开发者不只要考虑计算，还要面对数据分布、负载平衡、失败处理和容错。MapReduce 让你主要定义映射函数 map 和归约函数 reduce，把大量分布式管理交给框架。
A: 所以不是只有两个计算动作，而是我主要写两个函数，框架还要替我组织它们之间的数据流。
B: 我们手推一次。输入分成两片，split。第一片的地区依次是“北、南、北”，第二片是“南、北”。这些都是已经筛选过的高温记录，每片交给一个工作者。
A: map 就输出“北，一”“南，一”“北，一”；另一个工作者输出“南，一”“北，一”。我先不急着合并，因为同一地区散在不同工作者手里。
B: 接着是 shuffle，重分布并按键分组。北这个键对应的三个一被送到同一组，南对应两个一。最后 reduce 对每组求和，得到北三条、南两条。
A: 我按原记录核对：第一片两个北一个南，第二片一个北一个南，确实是北三南二。真正让分布式汇总成立的是按键汇合，不是各节点随便给一个总数。
B: 而 shuffle 可能跨网络，所以抽象隐藏管理细节，并没有消灭通信成本。回到平均温度，你需要保留温度和与记录数，再合并后求平均，不能丢掉权重。选对可合并的中间信息，也是开发者的责任。
A: 那框架负责调度和故障处理，不等于框架会替我证明统计逻辑正确。我们的温度汇总只是这套“提取键值、按键聚合”的一个用法。
B: 课件以 Apache Hadoop 为代表实现，强调简洁、扩展性和容错；还列出搜索索引、热门查询、新闻聚类，以及分类和聚类等机器学习任务。它不是只会数词，但也不是所有问题都天然适合一遍映射加归约。
A: 要是我在同一批模拟结果上反复分析，每轮都重新准备数据，那又会回到搬运和重复工作的老问题。下一个选择应该围绕“复用”，而不是围绕名字更新。
B: 假设我们要在同一批温度结果上不断调整分析参数。你会怎样避免每轮都从头搬数据？
A: 把数据保存在各节点内存里，下轮接着用。但一台机器失败会丢数据，难道复用就必须放弃容错？
B: Apache Spark 把 MapReduce 的思路推广到更丰富的操作，重点包括迭代任务和交互式集群分析。它的核心概念是弹性分布式数据集，Resilient Distributed Datasets，缩写 RDDs，单个叫 RDD。分布式说它分布在多处；弹性强调故障恢复能力。
A: 所以不是我手工在内存塞一份数组，就自动成了 RDD。它属于框架管理的数据抽象，既提供复用，也考虑失败。
B: RDD 支持把数据缓存在内存中复用，同时保持容错，而且操作不局限于 map 和 reduce。但“支持缓存”不是承诺所有数据永远装得进内存；更不是说 Spark 没有磁盘或网络开销。
A: 放到温度案例，值得缓存的是下一轮还要反复访问的那批数据。只用一次、又很大的东西，未必值得占住空间。
B: 再记一个上下关系即可：Spark Core 提供 RDD、变换等基础能力；上层有处理结构化查询的 Spark SQL、流式处理的 Spark Streaming、机器学习库和图计算库 GraphX。它们建立在核心之上，不是几台互不相关的机器。
A: 我先把它们记成同一底座上的不同入口，不把列出名称当成掌握 API。我们的分析若要反复从数据学习规律，接下来还要区分学习究竟在做什么。
A: 我想让程序根据已有模拟预测高温区域。这叫 AI 吧？那机器学习和深度学习只是它的另外两个名字？
B: 你的任务可以进入 AI 讨论，但这三个名字不是同义词。人工智能，Artificial Intelligence，简称 AI，是外圈，涵盖学习、推理、问题求解等方向。机器学习，Machine Learning，简称 ML，是其中从数据学习的一部分。
A: 那如果程序按人工写好的规则判断高温，不一定是在从数据学习。深度学习又是从数据学习里面更小的一圈？
B: 深度学习，Deep Learning，简称 DL，是机器学习的子集，使用深层神经网络等方法。课件把常见数值、类别数据与图像、文本等非结构化数据作对比，用来说明不同任务特点，不是在说普通机器学习绝不能处理图像。
A: 所以三层包含关系是 AI 包含 ML，ML 包含 DL。预测温度是一个具体任务，也不等于已经拥有能像人一样处理任何智力任务的通用智能。
B: 课件正是把面向特定任务的狭义 AI 与通用 AI 概念分开。现在假设我们选择从模拟数据训练模型，你会第一步就启动训练吗？
A: 我原本会。现在想想，温度单位混乱、缺值或异常记录，会把模型带偏。我应该先清洗、检查合理性，把输入整理成能比较的形式。
B: 这叫数据预处理，data preprocessing。原始输入可能是表格、时间序列、图像或文本；预处理可包括特征工程、格式转换、标准化或归一化，以及必要的降维。不是每个项目机械执行全部操作，而是根据数据问题选择。
A: 那我先用全部温度记录算标准化参数，最后再留一部分做评估，也算模型没见过它们吧？
B: 不算完全隔离。先划分数据角色；标准化、降维这类要从数据学参数的处理，只能在训练部分拟合，再原样应用到验证或测试部分。调模型用验证数据或交叉验证，每折的预处理也只从该折训练部分学习。最终测试数据不能反过来帮你选模型。
A: 所以温度模型没直接训练那批样本还不够，预处理和调参也不能偷看最终答案。然后训练，但模型把训练资料答得好，我能直接让它代替模拟吗？它也许只是适应了这些旧样本。
B: 所以流程图虽然把评估画在训练后，评估规则要在训练前设计好。模型训练，model training，要选择模型、优化器、损失函数和超参数。模型评估，model evaluation，要问它面对未用于拟合的数据是否可靠；分类可以看准确率、精确率、F1，预测连续温度这样的回归可看均方误差等，也可用多折交叉验证。
A: 最后才是推理，inference，把训练好的模型应用到没见过的新输入。我的地图是预处理、训练、评估、推理；训练改变模型参数，推理使用已有参数，不是一回事。
A: 阶段我懂了，但训练时我还想检查每次预测怎样变成参数修改。只知道启动训练，我就没法定位到底是哪一步出了问题。
B: 如果你还想控制每轮训练的具体动作，课件介绍了 PyTorch。它面向深度学习，提供 Python 和 C++ 前端；用 nn 包定义网络层，并允许手工安排训练与评估循环。重点是可控，而不只是调用一次黑盒命令。
A: 我猜训练循环是先给输入，得到预测，再拿预测和目标比较，接着改参数。还缺什么？
B: 你把预测、比较和修改连起来了，还差怎样确定往哪改。损失是预测与目标的差异尺度；梯度，gradient，描述损失对参数变化的敏感程度。反向传播，backpropagation，用来算这些梯度，优化器再据此更新参数。
A: 所以算出梯度还不是已经改了参数。我下一批温度样本来时，上一批的梯度会自动被覆盖吗？
B: PyTorch 默认会累加梯度。本例没有刻意做跨批累积，所以在这次反向传播前清掉旧梯度，再计算新梯度、更新参数；清掉的不是模型已经学到的权重。
