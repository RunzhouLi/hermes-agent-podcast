# EP03 — 线程一起工作，怎样不把结果做错？

## 本集怎么学

贯穿场景是一个订单处理服务：并行统计数组 → 共同领取最后一个名额 → 同时更新库存与账本。需要检验的是三类关系：**对象寿命、访问与业务同步、等待与进展**，不是背诵 API 名字。

先修：知道进程内线程共享地址空间，核心执行指令。对象寿命、独立结果槽和程序内先后顺序在本集随例补充。这里采用 C++17 的 `std::thread`、`std::mutex` 语义；不把它们的清理规则推广到所有语言和所有线程类型。

**学习成效尚未通过真实听众作答检验（learner_evidence: not_tested）。** 以下题目提供独立练习机会，不代表听众已经掌握；全部订单、名额、账本变式及解析为自编材料，不是教师发布的试题、标准答案或评分规则。

## 术语表

| 中文 / 英文 | 本集含义 | 不能误推成 |
|---|---|---|
| 进程 / process | 资源及保护边界；包括地址空间、代码、打开的文件等 | 进程只含一条执行流 |
| 线程 / thread | 进程中的执行流，具有自己的程序计数器、寄存器状态和调用栈 | 每条线程必定独占一个核心 |
| 并发 / concurrency | 多项工作可交错推进 | 必须同一时刻在不同核心执行 |
| 并行 / parallelism | 工作实际同时执行 | 只要创建线程就一定加速 |
| 汇合 / join | 等待所关联线程完成，并在成功返回时获得相应同步保证 | 启动线程；暂停所有其他线程 |
| 分离 / detach | 解除句柄与线程的关联，让线程可独立继续执行 | 等待完成；自动保存被引用的数据 |
| 可汇合状态 / joinable | 句柄仍有关联的线程需要处理；执行已经结束也可仍为此状态 | “此刻还在运行”检测器 |
| 悬空引用 / dangling reference | 引用的对象寿命已经结束 | 持锁就能重新访问 |
| RAII / Resource Acquisition Is Initialization | 资源责任与对象生命周期绑定，离开作用域时进行规定的清理 | 自动证明清理顺序正确或业务自动回滚 |
| 先行发生 / happens-before | 由程序顺序和有效同步等规则组成的先后关系 | 墙钟上看起来先发生 |
| 竞争条件 / race condition | 结果依赖不同线程的相对执行顺序 | 一律是bug，或一律是C++ data race |
| 数据竞争 / data race | 在本例范围内：潜在并发的冲突访问，至少一个非原子，且彼此没有所需happens-before | 只有写/写才算；只会丢更新 |
| 未定义行为 / undefined behavior，UB | 语言不再提供正常语义保证 | 可以用有限几种旧值列尽结果 |
| 互斥 / mutual exclusion | 相关线程不能同时进入受保护的临界区 | 每个线程最终一定进入 |
| 临界区 / critical region | 在同一同步协议下作为整体保护的代码区间 | 只需锁住最后一个赋值 |
| 不变量 / invariant | 业务在约定观察边界应一直满足的约束 | 任意一个变量的最终值看似正常就够了 |
| 死锁 / deadlock | 一组线程的等待依赖互相闭合，无法推进 | 任何短暂阻塞 |
| 饥饿 / starvation | 某线程永久得不到必要资源，其他线程仍可能不断完成 | 已证明所有线程都相互等待 |
| 安全性 / safety | “坏事不会发生”，如不重复发放名额 | “好事一定及时发生” |
| 活性、进展 / liveness | 在声明的前提下，相关工作能继续发生或完成 | 自动保证公平或下一毫秒完成 |

来源：S04物理页8–11；S05物理页4–8、14–25；S06物理页9–13；S07物理页15–16；data race及库语义按文末WG21 N4659定位澄清。

## 附录A：识别性内容与代码阅读入口

### A1. 资源图与状态图

S04物理页10对照的是“多个单线程进程”和“一个进程内的多条线程”。每线程的程序计数器、栈和寄存器状态与进程的共享地址空间分属不同维度。**栈通常由线程持有，不代表栈中对象的地址不能被传给别的线程。** 办公室/文件柜类比只帮助理解共享资源与独立执行位置，不代表语言自动提供访问权限或对象寿命保证。

S04物理页9的箭头可读作：

```text
创建 → ready（可运行） →[dispatch：调度]→ running（运行） → 终止
          ↑                                  │
          └──────────[preemption：抢占]────────┘
          ↑                                  │
          └─[I/O完成]─ blocked（等待） ←[I/O操作]─┘
```

事件完成后回到ready，仍需调度；不直接保证进入running。这是课件的进程生命周期图，用于澄清状态，不把所有线程库实现都简化成完全相同的状态机。

S05物理页4还区分了关注点：并行更侧重利用硬件改善算法性能，并发更侧重职责拆分和服务响应。二者可以结合；并发结构本身不保证加速，实际同时执行也不保证收益超过管理开销。

用户级线程由用户空间运行库管理，操作系统未必逐个看见；内核级线程由操作系统调度。S04物理页11的历史流行度评论不作为现代运行库的总论。此处识别调度层次，不讲具体映射策略。

### A2. 如何把工作交给线程

C++程序的初始线程运行`main()`；在本课模型中，`std::thread`用来表示额外的系统线程，声明位于`<thread>`。入口函数返回表示该执行流完成，不等于句柄管理责任已经解除。（S05物理页6–7）

S05物理页10–13提供三种启动工作形状：

| 形状 | 读代码时关注什么 |
|---|---|
| `std::thread t(do_work);` | 入口函数是`do_work`；还需要后续生命周期处理 |
| `std::thread t([/* captures */] { /* work */ });` | lambda形成可调用对象；捕获决定其携带的值或引用 |
| 定义`operator()`的类对象作为入口 | functor，即可被调用的对象；类的成员也可能携带引用 |

上表是语法阅读形状，不是可直接运行的完整程序。`[&]`和`[=]`在常见lambda中分别表示默认按引用捕获与默认按值捕获；不要据此推断“按值捕获自动深拷贝所有指针指向的数据”。本集只要求沿着捕获关系检查对象寿命，不展开完整捕获和模板规则。（S05物理页11–16）

线程标识类型为`std::thread::id`；句柄上的`get_id()`用于取得关联线程ID，`std::this_thread::get_id()`用于识别当前线程。课件用它区分主任务和共同工作；ID不是CPU核心编号，也不自动分配数组区间。（S05物理页8）

### A3. 移动的是责任，不是“又复制一个工人”

按S05物理页24–25的示例顺序做纸面追踪：

| 动作 | 执行流与句柄关联 |
|---|---|
| `t1`启动工作一 | `t1`关联工作一 |
| 新建`t2`并从`t1`移动构造 | `t2`接管工作一；`t1`变为空状态 |
| 向空的`t1`移动赋值一个新线程 | `t1`关联工作二；`t2`仍关联工作一 |
| 默认构造`t3`，再从`t2`移动赋值 | `t3`关联工作一；`t2`为空 |
| 未处理`t1`就用`t3`移动赋值覆盖`t1` | 目标`t1`仍joinable，会调用`std::terminate`；不能当作安全替换 |

最后一步是**错误路径说明，不建议运行来观察结果**。工作二即使已经执行结束，若句柄仍joinable，这个规则也不变。可先按合法协议处理原线程，再接收新责任；移到一个新建空句柄本身不会启动额外执行流。（WG21 N4659物理页1379）

S05物理页23关于lvalue/rvalue的简化表述不用于本集推理。若要扩展值类别、转发引用或泛型捕获，须另按指定C++版本核查；本附录提供阅读入口，不宣称完成该专题教学。

### A4. 队列表示的范围

S06物理页4–7从呼叫中心过渡到队列的入队、出队接口及共享head。物理页5的`head++ % QSIZE`、`tail++ % QSIZE`只是用取余选择数组槽的表示示意，不是已经处理空/满、计数边界与关闭协议的完整环形队列。本集S10保留这一动机，完整业务的保护推演见S11–S16；EP04.O1/O2延续状态谓词与等待协议，**不承诺讲授完整环形有界队列实现**。后者在此登记为未教学的可选工程扩展，不是本集四个掌握目标的必要先修。

## 附录B：完整手推与模型

### B1. 不冲突结果槽与join

自编输入：`[2,4,6,8]`。数组在启动前初始化，计算期间不再修改；槽甲、槽乙是两个不同的普通整数对象，不使用打包位容器。

| 对象 | 写入者 | 读取者 | 关键条件 |
|---|---|---|---|
| 订单数组 | 管理线程在启动前初始化 | 甲读前半，乙读后半 | 对象活到最后访问之后；工作期间只读 |
| 槽甲 | 甲 | 管理线程 | 管理线程在甲的join成功返回后读取 |
| 槽乙 | 乙 | 管理线程 | 管理线程在乙的join成功返回后读取 |

数值：`2+4=6`；`6+8=14`；`6+14=20`。

```text
管理线程：准备数组与结果槽 → 启动甲 → 启动乙 → join甲 → join乙 → 汇总 → 销毁
甲：                         读取前半 → 写槽甲=6 → 完成
乙：                                  读取后半 → 写槽乙=14 → 完成
```

上图只表示依赖，不按横向长度表示用时，也不规定甲乙谁先完成。每个工人的结果写入，通过该线程完成与对应join成功返回的同步关系，先行发生于后续读取。若只join甲，没有别的同步，不可因此使用槽乙。若甲乙已经对同一普通对象发生无序冲突，管理线程最后join不能追溯修复这个冲突。（S05物理页5–7；WG21 N4659物理页1379）

“已完成”只是讲解账本，不是共享的无同步布尔标志。程序不靠看见某个普通结果值、睡眠若干时间或“测试过很多次”作为完成证据。

### B2. 寿命修复与异常路径

错误关系：`建立局部对象 → 启动引用它的线程 → detach → 局部对象销毁 → 工人仍访问`。当发生最后一个动作时，引用已经悬空；加锁不能延长对象寿命。（S05物理页14–16）

正确关系至少要同时满足：

```text
工人对对象的最后访问  →  对象销毁
工人写结果 → 有效的完成/发布同步 → 消费者读取结果
```

一个修复是数据销毁前完成join；另一个修复是真正延长或转移数据所有权，并另外提供结果同步。复制指针不等于深拷贝其指向对象。

RAII教学顺序：先建立数据，再建立线程句柄，立即用本例不抛异常的构造为该线程建立守护对象。守护对象必须在数据之前析构。多个工人逐个纳入清理管理，避免后续启动或管理工作抛异常时留下无人处理的joinable句柄。合法清理还要求：不是线程自己join自己，句柄未被别人并发修改，守护对象引用的句柄仍有效，管理线程不持有工人完成必需的锁。（S05物理页18–22）

守护对象析构前检查`joinable()`：若正常路径已成功join，则不重复join；若因管理线程的异常退栈而尚未join，按上述合法前提等待。后续线程创建失败时，先前已经纳管的线程仍由各自守护对象清理；未成功建立的对象不参与正常析构序列。这里展示的是这个清理协议，不声称课件短类覆盖了所有join失败与异常传播情形。工作入口若漏出未捕获异常，会调用`terminate`，不是由`join`自动把异常交还管理线程。`std::thread`的析构不会自动join；析构或移动赋值覆盖joinable目标会调用terminate。（S05物理页19–22；WG21 N4659物理页1379–1380）

### B3. 最后一个名额：合法原子交错的业务错误

自编模型：初始库存1；所有库存操作均为SC原子load/store；每名工人拥有独立普通布尔成功槽，启动前均初始化为false，只有成功者改为true；主线程对两个工人都成功join后读取并汇总。业务只是内存中的名额授予，不包含网络支付、外部出票、失败回滚或异常。

| 步骤 | 动作 | 库存 | 甲之前的判断 | 乙之前的判断 |
|---|---|---:|---|---|
| 初始 | 尚未检查 | 1 | 未检查 | 未检查 |
| 甲检查 | 甲load得到1 | 1 | 通过 | 未检查 |
| 乙检查 | 乙load得到1 | 1 | 通过 | 通过 |
| 甲办理 | 写0，记录甲成功 | 0 | 已据此领取 | 通过 |
| 乙办理 | 写0，记录乙成功 | 0 | 已领取 | 已据此领取 |

最终库存0而成功次数2，违反“不补充名额时，成功领取次数至多1”。一次读或写的原子性不使复合业务原子化。

**普通C++对照**：若库存改为普通`int`，冲突访问至少一个非原子，且彼此缺乏所需happens-before，则为data race/UB。上表不是该UB程序的完整输出列表。一次读与一次写也可以构成data race，不要求双方都是写。（S06物理页9；纠正S07物理页16；WG21 N4659物理页32）

### B4. 完整临界区与“每一行都锁了”

正确自编协议：库存启动前初始化为1，两个独立普通布尔成功槽初始化为false；工作期间各工人只写自己的槽，主线程在对应join均成功后读取。

```text
reserve(自己的成功槽):
    获取大家共同使用的库存锁
    在锁内重新检查库存
    若库存 > 0:
        将库存置为0
        将自己的成功槽置为真
    离开此作用域时释放锁
```

甲先获锁时，先检查1、记录成功并更新0；乙之后获锁重新检查0，不再成功，自己的成功槽保持false。乙先获锁同理。业务记录操作假定不会失败，相关对象及mutex始终有效。

分段持锁反例：

```text
普通int库存；所有库存读写都使用同一mutex：
    持锁读取库存并保存“可以领取”判断；随后解锁
    ... 其他线程可以在这里行动 ...
    重新持锁；根据之前保存的判断写0并记录成功；随后解锁
```

两名工人可以先后在各自第一段读到1，再先后在第二段各自成功。库存访问可以没有data race，业务却仍有race condition。互斥协议必须覆盖所需的整个不变量，而不是仅让每次单独访问合法。（S06物理页9–11、15；分段持锁为自编迁移例）

### B5. 两把锁的等待环

自编库存/账本业务在操作期间同时需要两把独立锁；不考虑其他取消或外部释放路径。

| 线程 | 已持有 | 在等待 | 等待谁先行动 |
|---|---|---|---|
| 甲 | 库存锁 | 账本锁 | 乙 |
| 乙 | 账本锁 | 库存锁 | 甲 |

```text
甲 ──等待乙释放账本锁──→ 乙
甲 ←──等待甲释放库存锁── 乙
```

每把锁单独互斥，并不排除这个环。RAII只在退出作用域时清理；线程阻塞在获取第二把锁处，不能靠尚未发生的析构解围。

改成所有相关路径都按`库存 → 账本`获取后，乙在等待库存时不会先持有账本，从而消除**这类逆序锁环**。这不是对任意程序的无死锁证明：额外锁、线程join、I/O依赖等仍需另查。

没有环也不能推出公平或截止时间。永久得不到资源、其他线程却能持续完成，是饥饿；暂时等待不能单凭时长断言永久饥饿。即使获得库存锁，也只是取得检查机会，未必还有名额。（S06物理页13、16；S07物理页15–16）

## 附录C：锁包装器与多锁阅读

### C1. lock_guard与unique_lock

- `lock_guard<std::mutex>`的通常构造方式获取mutex，退出作用域时释放。其作用域应覆盖完整业务。课件计数器例把整个`++g_i`置于这一保护内；这并不允许其他入口继续无锁访问同一计数器。（S06物理页11、15）
- `unique_lock<Mutex>`管理一个可锁对象的所有权，可延迟获取、释放后再获取及移动所有权；条件等待如何使用它，见EP04.O1/O2。（S06物理页12）
- 包装器不改变底层锁的能力。普通`std::mutex`非递归；已持锁的同一个`unique_lock`再调用`lock()`，不是递归用法。定时获取也要求底层锁支持相应能力，不是把普通mutex包装起来就有了定时接口。（WG21 N4659物理页1382–1384、1393–1395）
- RAII负责解锁，不自动回滚已完成的写入或外部副作用。真实业务若会中途失败，还需独立的异常安全、事务或补偿设计；本集未构建这些机制。

### C2. std::lock与adopt_lock的职责

S06物理页16的swap例可以按以下伪代码阅读：

```text
swap(lhs, rhs):
    若lhs与rhs是同一个对象，直接返回
    std::lock(lhs.m, rhs.m)       // 使用死锁规避算法取得多把锁
    守护对象甲接管已经取得的lhs.m // adopt_lock：不要再次lock
    守护对象乙接管已经取得的rhs.m
    交换受保护的数据
    退出作用域时由守护对象释放锁
```

这里每个对象各有独立mutex，先排除自交换，也排除了把同一mutex作为两把锁传入。若工程设计允许不同对象共享同一mutex，还须另外检查锁的别名，不能只检查对象地址。

`adopt_lock`不是获取锁的动作，而是告诉包装器“调用线程已经持有这把锁，请接管释放责任”；遗漏前面的合法获取不符合前提。`std::lock`也不等于所有锁在一条原子指令中同时获得，不消除整个程序中的所有外部依赖。（S06物理页16）

## 独立练习：先做题，再展开解析

### EP03-T1｜题目与提示

对应讲稿S07；提示S08；解析S09。

数组`[3,5,7,9]`，甲算前半、乙算后半，各写不同普通整数槽。数组和槽都在`start()`的局部作用域中；函数把引用交给工人，随后detach并返回。调用者通过保留的引用，拿一把工人从不用的mutex读取槽。

1. 在一个进程框里画出主线程、甲、乙各自的执行位置与栈，并标出数组、槽甲、槽乙的读写者；主线程何时可以读结果？
2. 指出哪种缺陷拿锁也不能修复。给安全时间线，保留工作重叠机会，不把局部引用返回出去；若函数中途抛异常，哪个清理对象必须先于数据析构？
3. 报出修复后的两个小计和总和；只有一个核心会不会改变安全判断？
4. 已结束但未join的线程句柄，能否被另一个线程句柄移动赋值覆盖？和移动到新建空句柄有何区别？

**先按暂停或遮住解析。** 可选提示：分别检查“最后访问→销毁”和“写结果→同步→读结果”；句柄管理责任和执行是否结束是两件事。

### EP03-A1｜解析与自查要点

- **O1标准**：数组启动前初始化，工人只读；甲独写槽甲，乙独写槽乙；主线程最终读取两个槽。线程有各自执行状态，不要求多核同时执行。
- **O2寿命标准**：detach不续命。函数返回销毁局部对象，工人及调用者留下的引用都可能失效。锁不能修复对象已经销毁的问题。
- **O2同步标准**：工人不使用调用者的mutex，调用者单方面拿锁没有建立相应同步；即使把对象寿命延长，也不能跳过结果同步。
- **一种修复**：创建数组及槽 → 启动甲、乙并各自纳入清理管理 → 各自最后访问及完成 → 对应join成功返回 → 读取槽8和16 → 汇总24并按值返回 → 销毁局部对象。两条工人链可交错；等待位置不应让乙直到甲结束后才启动。
- **异常与句柄标准**：管理线程异常退栈也须先由守护对象等待相关工作，再销毁数据；函数末尾的手写join可能被跳过。守护对象及时以不抛异常的构造建立，析构只对仍joinable的句柄join，不能在正常路径已join后重复等待。执行结束不等于不joinable；对joinable目标移动赋值会terminate。移动到新建空句柄只转移责任，新句柄仍须合法处理。工作入口未捕获异常不由join转交，见附录B2。

常见不足：只答24；只说“加mutex”；把返回局部槽引用当作安全结果；用睡眠替代完成同步。

### EP03-T2｜题目与提示

对应讲稿S14；提示S15；解析S16。

库存为SC atomic，初值1；两个独立普通布尔成功槽启动前均初始化为false。每位工人执行`if(load()>0)`，然后`store(0)`并把自己的成功槽改为true；失败者保持false。结果在对应join均成功后汇总。

1. 能否两次出票？写出交错及业务不变量。
2. 换成普通`int`，其余仍无同步：能否枚举最终库存作为完整C++答案？
3. 同一把mutex应覆盖哪段？为什么只锁store不够？
4. **新的迁移变式**：所有普通库存读写都拿同一把mutex，但检查和更新是两个持锁区间，中间解锁。库存访问是否仍有data race？业务是否仍可能错？

可选提示：分别说出原子的单位、同步连接的访问，以及需要整体保护的决定。

### EP03-A2｜解析与自查要点

- 原子版本可出现`甲load1 → 乙load1 → 甲store0并成功 → 乙store0并成功`。最终库存0、成功次数2，违反初始一个名额最多成功一次的约束。
- 普通无同步版本先判data race/UB，不列“仅可能为0或1”等伪完整清单。读/写冲突就足够，不要求两边都写。
- 完整锁版本从检查前开始保护，覆盖检查、成功决定/记录、库存更新。后获锁者重新检查当前库存；所有入口须遵守同一协议。
- 分段持锁版本中，甲检查1后解锁，乙检查1后解锁，随后两人分别拿锁更新0并成功。所有库存访问都被同一mutex排序，可以没有该库存的data race，却仍有业务逻辑竞争。

**O3标准**：能分别判断语言合法性和业务不变量，并能解释锁区间边界；不是只写“atomic安全”或“出现锁就安全”。

### EP03-T3｜题目与提示

对应讲稿S19；提示S20；解析S21。

甲按库存锁→账本锁获取，乙按账本锁→库存锁获取；各持第一把且等待第二把，拿齐后才能释放。

1. 画持有/等待表及等待环。使用RAII是否已经足以排除问题？
2. 全部改为库存锁→账本锁，消除了什么？能保证乙下一毫秒买到票吗？
3. 如果其他工人持续完成，乙却永久得不到必要资源，如何分类？如果只是暂时等待呢？
4. 若名义上的两个对象其实是同一对象，多锁调用前应检查什么？
5. **新的迁移变式**：甲持有库存锁时join乙，乙必须取得库存锁才能结束。只有一把锁是否仍有等待环？一致锁序是否足够？

可选提示：没有等待环，不等于公平、有限持锁时间或库存充足。

### EP03-A3｜解析与自查要点

- 甲持库存等乙的账本，乙持账本等甲的库存，形成环。题设中没有其他释放路径，相关线程死锁；RAII的析构尚未发生。
- 统一次序排除这类逆序锁环，前提是全部相关路径遵守规则且没有新增依赖。不能据此承诺公平或一毫秒截止时间。
- 取得锁只意味着获得重新检查机会，不保证还有库存。
- 其他线程持续完成而乙永久得不到资源，属于饥饿；暂时等候尚不足以证明饥饿。
- 排除自交换及同一mutex的重复获取。普通mutex不能因为被不同包装器引用，就算成两把独立锁。
- 新变式中甲等待乙完成，乙等待甲释放库存锁，仍构成环。它不是多锁逆序，不能只靠锁序修复；甲应完成受保护操作并释放乙所需的锁，再join。等待图必须纳入线程完成依赖。

**O4标准**：等待环和修复理由都要画出；把安全性、整体进展、个体公平和时间承诺分开。
