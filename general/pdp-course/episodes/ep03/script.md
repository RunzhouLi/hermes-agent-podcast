# EP03 — 线程一起工作，怎样不把结果做错？

## S01 — 同一个服务的三道关
A: 我们的订单处理服务要加两名工人。先让他们分头统计订单，再共同领取处理名额，最后把名额变化记到账本里。是不是每个阶段套上线程，速度就上来了？
B: 先别承诺速度。今天要让这个服务过三道关：工人访问数据时，数据还活着；多人办理一次业务时，不把业务拆坏；需要互相配合时，不会等成一圈。我们沿着同一个服务往下改，不把线程和锁当作孤立的按钮。
A: 那我最后要交的不是几个接口名字，而是一份说明：谁访问哪个对象，访问发生在什么时候，等不到时到底在等谁。
B: 对。我们会用 C++ 的线程模型讲这些关系。原课件还会继续讨论任务、同步粒度和向量化，本集先把生命周期、共享状态、互斥和进展接起来。中间有三道自编变式，请真的停下来作答。
> 来源：S04《Shared Memory I》物理页4；本集订单服务为自编贯穿场景，不是课件原题。

## S02 — 同一间屋子，不同的执行位置
A: 先说两名工人住在哪里。第一集说同一进程里的线程共享地址空间，那他们是不是连做到哪一步也共享？
B: 不共享执行位置。进程，process，可以先理解为一组资源及其保护边界：地址空间、程序代码、打开的文件等。线程，thread，是其中的一条执行流。每条线程有自己的程序计数器，也就是下一步执行在哪里，还有自己的寄存器状态和调用栈。
A: 像一个办公室共用文件柜，但两个人各有书签和工作便签。甲在加第二个数，乙可以已经写完结果。
B: 这个比喻有一个重要限制：线程的栈通常各自管理，却不是别人绝对进不去的保险柜。把栈上对象的地址或引用交给别的线程，对方就可能访问它。共享与否要看地址和访问关系，不能只看变量写在哪个函数里。
A: 那两条执行流一定正在两个核心上同时跑吗？
B: 不一定。并发，concurrency，强调多项工作可以在时间上交错推进；一个核心轮流执行两条线程，也有并发。并行，parallelism，强调实际同时执行。启动两条线程不保证它们此刻同时占着两个核，也不保证会加速。
A: 调度图里的 ready，就是已经在执行吗？
B: 是可运行，不是正在运行。原图从创建进入 ready，调度后才到 running；被抢占会从 running 回到 ready。等待输入输出时进入 blocked，事件完成后回 ready，还要再等调度，不会自动跳到 running。最后执行结束才到终止。
A: 所以“已经启动”“可以运行”“此刻运行”“已经完成”是四种不同判断。
B: 对。用户级线程和内核级线程则是在问，哪些执行单元由运行库管理，哪些由操作系统调度。这里只需识别层次；不把历史课件里的流行度判断当作今天所有系统的结论。
> 来源：S04《Shared Memory I》物理页8–11，已读物理页9状态图、页10资源图；S05《Shared Memory II》物理页4–6。

## S03 — 先让共享不等于争抢
B: 现在只有一份只读订单数组，依次是二、四、六、八。甲负责前两项，乙负责后两项。另放两个不重叠的普通整数结果槽，槽甲只给甲写，槽乙只给乙写。数组在启动之前准备好，在两名工人结束之前一直保留。
A: 我先画三行：数组，两个人读；槽甲，甲写；槽乙，乙写。主线程要汇总，所以最后会读两个槽。
B: 正好。甲先把二加四，得到六；乙把六加八，得到十四。允许乙先完成。此时我们的讲解账本写着：乙已完成，槽乙十四；甲未完成，槽甲还不能当结果用。等甲也完成，槽甲才是六。
A: 数组共享，但没有人修改它。结果也在共同地址空间里，却写向两个不同对象，所以不是每次访问都要抢同一把锁。
B: 是这个理由。我们讲的“已完成”是旁观者描述状态，不是让程序无同步地轮询一个普通布尔变量。主线程如何可靠确认完成，马上要补上。
A: 能不能干脆让甲乙都把小计加进同一个总和？这样只留一个槽。
B: 可以设计那种算法，但就新增了共享更新的协调责任。先保留独立结果槽，最后集中汇总，能把不必要的冲突从设计中去掉。不是线程越多越需要锁，而是冲突访问才要求相应的同步协议。
> 来源：S04《Shared Memory I》物理页10；S05《Shared Memory II》物理页5–7；数组与结果槽示例改编自自编讲解《进程、线程与资源生命周期：从零讲解》。

## S04 — 等待要放在依赖的前面
A: 我启动甲，立刻等甲；再启动乙，立刻等乙。结果应该是对的吧？
B: 在其余前提满足时可以对，但甲乙没有重叠工作的机会。这里更合适的是先启动甲和乙，再等待它们，最后读结果。我们把等待线程完成的操作叫 join，中文可以理解为汇合。
A: 主线程先对甲 join，是否会把乙也暂停？
B: 不会。阻塞的是发起等待的主线程，乙仍然有机会继续工作。甲的 join 成功返回，保证甲已完成；想使用乙的结果，还得等乙对应的 join 成功返回。
A: 所以我不能看到槽里似乎已经有个数，就把它当作完成通知。
B: 对。join 不只是多等一会儿，它提供同步关系。甲写结果，甲结束，主线程对甲的 join 返回，然后主线程读槽甲，这条链建立了先行发生关系，happens-before。你现在可以把它理解为有语言规则保证的先后约束，不是凭时钟猜谁先做完。
A: 两个 join 都返回，主线程读六和十四，相加二十。它没有规定甲乙的完成顺序，只规定汇总必须在需要的结果完成之后。
B: 也没有把甲乙相互之间的所有访问都排好队。如果两个工人原本就在乱写同一个普通对象，主线程最后 join，不能倒过来消除他们之间已经存在的数据竞争。
> 来源：S05《Shared Memory II》物理页5–7；同步语义核对 WG21 N4659，物理页1379 [thread.thread.member]；数值为自编例。

## S05 — 句柄离开了，数据不能先离开
A: 服务不想在启动函数里等。能不能把数组放在 start 函数里，启动两个引用它的线程，调用 detach，然后返回？
B: detach 是分离：句柄不再负责通过 join 等待那条执行流，并不是让工人立刻做完，也不是替它保存所有数据。把时间线读出来：函数建立局部数组，工人取得引用，工人被分离，函数返回，数组寿命结束；如果工人随后还读取那个数组，访问的对象已经不存在。
A: 也就是 dangling reference，悬空引用。测试时偶尔算对，不能证明这条时间线安全。
B: 对。错误不在于工人“跑得不够快”，而在于设计允许销毁先于最后一次访问。加个睡眠拖延返回，也没有建立所需的完成保证。
A: 那我给每次读数组加锁呢？保证大家一个一个读，总该安全了。
B: 锁不能复活数据。你可以拿着一把完全正常的锁，去访问一个已经销毁的对象。首先要解决寿命：或者在数据销毁之前 join；或者把数据的真正所有权交给任务，让对象活到最后一次访问之后。
A: 所谓按值捕获，是不是肯定复制了整份订单？
B: 要看捕获的东西。如果复制的是拥有内容的值对象，可以形成独立数据；如果只复制一个指针，通常只是多复制了一个地址，不是把它指向的内容深拷贝。寿命方案之外，主线程读取结果仍需要同步，不能把“对象还在”和“结果已经可以读”合并成一个问题。
> 来源：S05《Shared Memory II》物理页10–11、14–16；逐步揭示页的“仍在运行”和“悬空引用”分别保留；自编讲解《进程、线程与资源生命周期：从零讲解》。

## S06 — 清理责任也有主人
A: 我把 join 写在函数最后一行。如果前面抛异常，那一行不就被跳过去了？
B: 所以要把清理责任绑定给对象。这种习惯叫 RAII，全称 Resource Acquisition Is Initialization。名字强调获取资源与初始化绑定，使用时还要记住另一半：对象离开作用域时，析构负责清理。
A: 给线程配个守护对象，让它在正常退出作用域，或异常沿调用栈退回、销毁局部对象时等待线程。
B: 但排列必须正确。在这类局部对象例子里，先创建数据，再创建线程句柄，紧接着用本例不会抛异常的构造安装守护对象。同一作用域的局部对象逆序析构，因此守护对象先等待，随后清理线程句柄，最后才销毁数据。多个线程要逐个及时纳入管理，别等全启动完才想起清理。
A: 也就是说，“用了 RAII”不是证明；要指出它到底在什么时候做什么。
B: 对。守护对象只对仍然 joinable 的句柄 join，正常路径已经等完，就不再重复等待。这里由管理线程对合法句柄清理，不等待自己，也不占着工人完成所需的锁。课件的简短守护类说明的是这个协议，不是处理所有库错误的通用实现。
A: 这里说的异常清理，是管理线程退出局部作用域时的责任，不是保证工人的异常会经 join 传回来。
B: 正是。工作入口若漏出未捕获异常，std::thread 会调用 terminate，不能指望主线程的守护对象替它兜底。
A: std::thread 本身出了作用域，会自动 join 吗？
B: 不会。若析构时仍是 joinable，就会调用 terminate。joinable 要理解为句柄仍关联着需要处理的线程，不等于线程此刻还在运行。执行函数已经返回，也可能仍然 joinable。
A: 清理责任能从句柄甲交给句柄乙吗？
B: 能，用移动，move。std::thread 可移动、不可复制。移到一个新的空句柄后，新句柄接管同一条线程，原句柄变空；没有额外启动一名工人。如果移动赋值的目标原本仍然 joinable，直接覆盖会 terminate，不能把覆盖当作回收。具体值类别和语法放在附录，不靠背符号判断责任。
> 来源：S05《Shared Memory II》物理页18–25；已逐页阅读物理页19–22的守护对象例证；工作入口未捕获异常、析构、移动赋值语义核对 WG21 N4659 物理页1379；页23值类别简化不沿用。

## S09 — EP03-A1 解析
A: 一个进程框里放三条执行流：主线程、甲、乙，各有执行位置和栈。数组由主线程启动前初始化，随后甲乙只读；甲只写槽甲，乙只写槽乙。主线程不能在工作期间随意读这些普通结果槽。槽不冲突解决了工人之间的写入问题，没有自动解决汇总时机。
B: 更早的缺陷是局部对象在函数返回时销毁。留下的引用不会延长寿命，调用者后来持锁也无法修复。工人根本不使用这把锁，单方面加锁也没有为它们的写入建立同步。
A: 我把程序改成：创建数组和槽，启动甲和乙；工人各自最后访问并结束；对应 join 返回；主线程读取两个结果，汇总后按值返回，再让局部对象销毁。不再把局部槽的引用带出函数。
B: 数字是三加五得到八，七加九得到十六，总和二十四。两个最后访问可以交错，两个 join 也不规定工人谁先结束。一个核只改变执行机会，不会让已经销毁的对象重新有效。用真正持有数据的任务也能修复寿命，但还要另有结果同步。
A: 异常退出时，要先由守护对象等待相关工作结束，再销毁数据；写在函数末尾的 join 可能被跳过。已结束但未 join 的句柄，可能仍然 joinable，所以不能直接移动赋值覆盖。移到空句柄则只是交接责任，新的主人仍要妥善处理它。
> 来源：自编 EP03-A1；数字经工具复算；句柄规则见 S05 物理页24–25及 WG21 N4659 物理页1379。

## S10 — 从分工表走到共享队头
A: 统计结果现在能安全汇总了。但真实服务不止处理固定的一批数组，还会不断收到新订单。
B: 所以会有等待队列。课件用呼叫中心说明：来电先排队，空闲接线员取走一个。换到我们的服务，订单入队，工人出队。队列这个抽象数据类型，ADT，规定了这些操作的意义；内部可以用数组，并用 head 标记队头、tail 标记队尾。
A: 只要把 head 往后移，下一位工人就能取下一单，看起来很简单。
B: 但谁负责“取当前单并移动队头”这个整体？原图把两名工人和会向后移动的 head 画在一起，提醒我们检查交错。若没有完整协议，两人可能都认定同一单归自己。图是问题提示，不是已经证明安全的执行记录。
A: 原来不同结果槽只是局部解法。到了共同领取任务，就要保护共享决定。
B: 为了听清这个决定，我们先把队列缩成最后一个处理名额。它像一张票：只能有一名工人领到。空队列该怎么等待，留到下一集；这一集先问，非空时怎样不重复领取。
> 来源：S06《Shared Memory III》物理页4–7；已读页7队头图；队列等待延续至 EP04。

## S11 — 每一步完整，不等于整件事完整
B: 名额库存初值是一。先声明一个抽象模型：每次读库存、写库存都是顺序一致的原子操作，英文 sequentially consistent，简称 SC。你可以把这些操作排成一个保留各线程自身顺序的交错序列。这里不讨论普通整数的无同步读写。
A: “原子”意味着这次读或写是不可拆分的一步，但检查后做决定、再更新，是好几步。
B: 正是。两名工人都按这个业务执行：读库存；若大于零，就认定领取成功，把库存写成零。成功记录各存在自己的普通布尔槽里，启动前都初始化为假，只有领取成功才改为真；主线程对两人都 join 成功后再汇总，避免又引入一个共享计数器的问题。
A: 我跟着报状态。甲读到一，检查通过，还没有更新。此时库存仍是一。
B: 乙接着也读到一，检查也通过。接下来甲领取成功，把库存写零；乙按照自己之前通过的检查，也领取成功，再把库存写零。
A: 最后的库存是零，但两个成功记录都是真的。看库存没有变成负数，反而容易以为没有超卖。
B: 这就是为什么正确性不能只盯一个最终数字。我们的业务不变量是：初始只有一个名额，没有补充时，成功领取的总次数至多一次。刚才每次原子访问都完整，整个业务却破坏了这个约束。
A: 这类依赖交错顺序的问题叫 race condition，竞争条件。顺序影响结果未必都是错误，例如先接待谁可以变化；真正错误的是出现业务禁止的结果。
> 来源：S06《Shared Memory III》物理页9；S07《Shared Memory IV》物理页16；本节 SC 原子库存和独立成功槽为自编抽象模型。

## S12 — C++ 合法性要先判断
A: 如果我把刚才的原子库存换成普通 int，不加任何同步，是不是仍只分析“发一张还是两张”？
B: 不能。这里要先判断数据竞争，data race。对于我们这些对象访问，先找不同线程是否访问同一个内存位置，且至少一个在写，也就是冲突；再看是否至少一个访问不是原子的；最后查它们之间是否缺少 happens-before。满足相应条件，就构成 C++ 的数据竞争。
A: 只要一边写，另一边只是读，也可能满足，不要求双方都写。
B: 对。两边都只读，一般没有这类冲突；但读的对象仍须活着。并且“并发冲突”不是必须两条机器指令在同一纳秒撞上。没有所需的同步先后关系，靠一次运行中看似错开，不能给程序证明合法。
A: 这个错误的后果是 undefined behavior，未定义行为，简称 UB。
B: 也就是 C++ 不再为这次有数据竞争的执行提供正常语义保证。不能把答案限制为库存零或一，不能只说偶尔丢一次更新，也不能用几次测试的输出证明结果只有那么几种。我们刚才的交错手推成立，是因为先声明了合法的 SC 原子模型。
A: 所以是两道门：先检查访问在语言层面是否合法，再检查合法执行会不会破坏业务不变量。
B: 没错。换成原子变量可以解决这例中库存访问的数据竞争，却没有让检查和领取自动变成一个事务；换回普通变量又不建立同步，两道门就可能一起出问题。下一步用同一把锁保护完整业务。
> 来源：S06《Shared Memory III》物理页9；S07《Shared Memory IV》物理页16须按至少一方写纠正；WG21 N4659 物理页32 [intro.races]/20及本地说明《共享内存与GPU：来源澄清及模型边界》§1。

## S13 — 把哪一段放进同一扇门
B: 互斥，mutual exclusion，要求相关线程不能同时进入受保护的临界区，critical region。mutex 是实现这种协调的互斥锁。名额服务的协议是：所有相关访问用同一把锁；拿到锁之后才检查库存，条件成立才记录成功并更新，完成这段业务之后再释放。
A: 重放刚才的场景。甲拿到锁，读一，领取，写零。乙想拿锁，暂时过不去。
B: 甲释放后，乙成功获得同一把锁，在锁内重新检查，读到零，就不领取，自己的成功槽保持假。注意乙并不是带着锁外那次“看见一”的结论直接进来办业务。
A: 如果只给最后的写零加锁，甲乙仍然可以在前面都通过检查。就算每次访问本身已经原子，业务还是错。
B: 对。若普通库存的检查还留在锁外，更可能另有 data race。锁不会给变量施魔法：有人绕过协议直接访问，或者每个人锁的是不同 mutex，都不受这扇共同的门保护。
A: mutex 除了挡住别人，还怎样连接到前面说的先行发生？
B: 对同一个 mutex，前一次释放与之后成功取得锁形成同步。甲锁内更新，甲释放，乙获锁，乙锁内检查，这条链给出了所需顺序。所以不能把它讲成“缓存差不多刷新了”。
A: 业务中途返回或者抛异常，也得记得解锁。
B: 这时 RAII 又出现了。lock_guard 的常见用法是在构造时拿锁，离开作用域时释放；因此守护对象的作用域必须覆盖整段业务。全局计数器加一的例子也是如此，要保护整个更新，而不是挑其中一个动作。自动解锁不等于自动撤销已经发生的业务，本例先假定成功记录和库存更新不会抛异常，也不包含网络出票。
A: unique_lock 呢？名字听起来像更强的一把锁。
B: 它是更灵活的锁所有权包装器，不是另一种神奇的锁。它可以先不获取、在合适时机释放再获取，条件等待会用到它，下一集再展开。它不会把普通 std::mutex 变成递归锁；同一个 unique_lock 已经持锁时再调用 lock，也不是合法的递归入口。
> 来源：S06《Shared Memory III》物理页10–12、15；S07《Shared Memory IV》物理页15；S06页12的 recursive locking 表述按本地澄清§2及 WG21 N4659物理页1382–1384、1393–1395限定。

## S17 — 两个局部安全，合起来会怎样
A: 服务又添了账本。一次领取要同时改变库存和账本；库存有库存锁，账本有账本锁。两份数据分别保护了，是不是就结束了？
B: 还要看组合。假设业务操作要同时持有两把锁，所有相关读写也遵守约定。甲先拿库存锁，再拿账本锁；乙却先拿账本锁，再拿库存锁。现在只记两列：已经持有谁，还在等待谁。
A: 第一行，甲持有库存锁。第二行，乙持有账本锁。接着甲等账本锁，而那把锁在乙手里。
B: 然后乙等库存锁，那把锁在甲手里。画等待箭头：甲指向乙，乙又指向甲。两人都要拿到第二把锁才能做完业务并退出，于是形成环。
A: 这是 deadlock，死锁。不是数据被两个人同时写坏，而是相关操作谁也走不到后面。
B: 对。这两把锁各自仍可能完美地实现互斥，名额也没有被重复发放，但服务卡住了。安全性，safety，问坏事会不会发生；进展或活性，liveness，问该完成的工作能否继续发生。这是不同的证明任务。
A: 给两把锁都装 lock_guard，析构自动释放，能不能解开这个环？
B: 不能。它们此刻卡在获取第二把锁的位置，还没离开作用域，析构根本没有发生。RAII 解决离开时的清理责任，不自动决定多个资源之间的获取顺序。

## S18 — 拆掉等待环，还剩什么承诺
B: 先用一条共同规则修复：凡是同时需要这两把锁，都先库存，后账本。假设甲先拿到库存锁，乙只能在第一把锁前等待，不能先把账本锁占住。
A: 这样甲等账本的时候，乙不会拿着账本反过来等甲的库存。那条返回的箭头被切断了。
B: 对。在所有相关路径都遵循规则、没有额外依赖的前提下，这个逆序拿锁造成的环不能形成。甲取得两把锁、完成业务并释放，乙才有机会继续。推广到更多锁，要有大家一致遵守的全局顺序，不是每个函数各自选一个顺序。
A: 所以我能承诺乙马上得到锁吗？
B: 不能。一致锁序不等于公平排队，也没有给出墙钟时间上限。即使没有死锁，某个线程也可能反复得不到所需资源，而其他线程持续完成；永久这样下去叫 starvation，饥饿。暂时等得久，还不能仅凭观察就断言永久饥饿。
A: 我把三个句子分开：互斥是不能一起进入；没有这种死锁是不存在这种等待环；没有饥饿是不能永远亏待某一个线程。
B: 还要给进展说明调度和业务完成的前提。别人持锁后永远不获调度，或者锁内业务本身无限等待，统一锁序也不能替它完成工作。
A: 课件还有多锁获取工具，能代替自己约定次序吗？
B: 对一组适用的锁，可以使用带死锁规避的多锁获取操作，附录介绍 std::lock 和接管已有锁的包装方式。但不是“一用工具，整个程序就没有死锁”。还得审查外部依赖，尤其先检查两个参数是不是同一对象。自交换时若把同一把非递归 mutex 当成两把去获取，前提就坏了。
> 来源：S06《Shared Memory III》物理页13、16，保留self-swap检查；S07《Shared Memory IV》物理页15–16。进展结论限定于已声明的等待模型，不承诺公平或截止时间。
