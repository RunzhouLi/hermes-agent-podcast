# EP04 — 什么时候等待，什么时候继续做别的事？

## S01 — 作业服务的两次停顿
A: 上一讲，我们给作业服务的共享数据加了锁。现在每次取订单都规规矩矩持锁，可服务还是会停住：有时候队列空了，有时候一批订单还没排完序。这两种停顿，都该让线程站在原地等吗？
B: 先别把它们归成一个问题。队列空了，是取订单所需的条件还不成立；排序没结束，是某一次计算的结果还没准备好。这一讲，我们跟着同一个服务，从订单入队走到批次排序，决定哪里必须等，哪里还有别的工作可做。
A: 所以不只是学两个会阻塞的接口，而是解释为什么在这里阻塞。
B: 对。先沿用上一讲的约定：访问队列的人都用同一把互斥锁，mutex，队列和锁活得比使用它们的线程久。我们的教学队列暂不设容量上限，先只讨论成功入队、成功取出的正常路径。关闭服务和异常处理，另有边界，不能悄悄假定已经解决。
> 来源：S07《Concepts and Models of Parallel and Data-centric Programming — Shared Memory IV》物理页4–5、12–13；S08《Concepts and Models of Parallel and Data-centric Programming — Shared Memory V》物理页4–7。作业服务为自编贯穿例。

## S02 — 拿着钥匙等订单
B: 把队列叫作Q。生产者把新订单放在队尾，消费者从队首拿走订单。数组、链表都可能用来实现队列，但不管怎么存，空队列都没有可以取出的队首。
A: 那我拿锁，检查Q为空，就一直等到它不空。锁还在我手上，别人不会把检查结果改掉。
B: 也正因为锁还在你手上，生产者没法入队。你等它改变状态，却挡住了它改变状态的路。互斥保证不同时乱改，不会凭空制造订单。
A: 我可以放锁，隔一阵再拿锁看一下。
B: 这叫轮询，polling。只要每次检查都持锁，生产者也用同一锁修改状态，这种反复查看可以作为一种等待办法。但频繁查会做无用功；查得稀，订单来了又可能等到下一次查看才被发现。讲义的示例选择睡一小段时间再检查，它并不是每次都能及时响应。
A: 我真正想要的是：现在没活就休息，来了活再提醒我。又不能为了休息，把生产者永远锁在门外。
B: 条件变量，condition variable，就是这个等待协议里的通知工具。但提醒不是订单本身，也不是获得订单的承诺。我们得先说清楚，醒来以后究竟查什么。
> 来源：S07《Shared Memory IV》物理页4–5、7–10。轮询与条件变量的对照采用同一mutex保护状态的前提。

## S03 — 把检查与入睡接起来
B: 我们要查的条件是：Q非空。把一个返回真或假的检查叫作谓词，predicate。这里不是另造一个容易过期的通知计数，而是直接问队列里面有没有作业。
A: 谓词为真，就能取；为假，就等待。这和普通的判断语句有什么不同？
B: 不同在检查之后。消费者先持锁检查。若为空，调用条件变量的wait。wait把释放这把锁和进入条件变量等待，作为一个不可被普通程序步骤拆开的动作。生产者随后才能拿同一把锁改变Q。不能自己先unlock，再慢慢安排一个等待通知的sleep；中间会留下漏掉通知的窗口。
A: 那wait是在等待期间放开锁，还是从调用以后就再也不管锁了？
B: 只在等待期间放开。被唤醒之后，它还必须重新取得那一把mutex，才会从普通wait返回。若别人正持锁，醒来的线程还得等锁。所以被唤醒、拿到锁、能够取作业，是三个不同判断。
A: 这个过程用哪种锁的包装器？
B: 这里用unique_lock，管理锁所有权的RAII包装器。它允许wait临时释放再重新取得锁；离开作用域时，如果仍持锁，就负责释放。lock_guard不能用于这个wait接口。还有个继承自上一讲的限制：unique_lock不会把普通mutex变成可重入锁，更不是让同一线程拿着锁再锁一次。
B: 带谓词的wait会替我们做循环：先检查，假就释放锁并等待，醒后重获锁，再检查。只有谓词为真才继续到取出代码。这才是我们接下来要手推的完整协议。
> 来源：S06《Concepts and Models of Parallel and Data-centric Programming — Shared Memory III》物理页12，与EP03共享复习；S07《Shared Memory IV》物理页9、13；WG21 N4659《C++17 Working Draft》物理页1404–1405，[thread.condition.condvar]/9–18。unique_lock边界按《共享内存与GPU：来源澄清及模型边界》§2澄清。

## S04 — 作业十二的交接
B: 现在只跟踪三件事：Q里有什么，谁持锁，谁在等。初态Q为空。消费者甲拿到锁，检查为空。此时持锁者是甲，还没有人在条件变量上等待。
A: 甲调用带谓词的wait。条件为假，甲交出锁并进入等待。现在Q仍为空，锁没有持有者，等待者是甲。
B: 接着生产者乙取得锁，放入作业12。此时Q里有12，持锁者是乙，甲仍在等待。乙释放锁，再调用notify_one，通知一个等待者。这里只有甲，于是甲被唤醒，但通知不会把mutex直接交到甲手里。
A: 假定这次没有别人抢先，甲重新取得锁。现在Q里还是12，谓词为真，甲读队首并删除12。删完Q又空了，最后才释放锁。
B: 注意甲成功检查到非空以后，直到读出和删除结束，中间没有再放锁。否则刚确认有货，货就可能被别人拿走。
A: 我看到有的代码是在生产者的锁还没释放时就notify。是不是一定错？
B: 不一定。乙可以在持锁改好Q以后通知，再释放锁。即使甲已经被唤醒，也得等乙放锁，才能重新获取mutex。先解锁再通知是可用写法，不是唯一合法次序。真正不能删的是：大家按同一锁保护队列，消费者醒后重获锁，再查谓词。通知次序的成本还取决于实现，不能拿一种写法当所有机器上的速度保证。
> 来源：S07《Shared Memory IV》物理页9与13的两种通知次序、物理页12–13的队列骨架；WG21 N4659物理页1404–1405，[thread.condition.condvar]/7–18。作业12状态推演为自编。

## S05 — 提醒声没有预留名额
B: 重演刚才的过程，但加一个消费者丙。乙已经放入12并通知甲。甲醒了，还没有拿到锁。这时丙先拿锁，发现Q非空，取走12，然后释放锁。
A: 等甲终于拿到锁，Q已经空了。不过甲确实收到过通知。
B: 通知是真的，作业也确实来过，但现在已经被取走。若甲只在最早用一个if检查一次，醒来就直接读队首，它会在空队列上做不合法的取出。带谓词的wait会再次检查，发现为空，就重新释放锁并等待。
A: 这次根本没发生虚假的通知，只是别人先到。也就是说，复查不只是为了防伪唤醒。
B: 对。伪唤醒，spurious wakeup，指没有对应通知也可能结束这次阻塞。它是额外一个必须复查的理由。但即使某次执行完全没有伪唤醒，丙抢先取走作业这个反例仍成立。唤醒只让甲有机会回来争锁，不是给甲保留一份作业。
A: 反过来，如果乙先放入12，通知时根本没人等，之后甲才来，那甲会不会因为没听到提醒而永远睡下？
B: 按正确协议不会。甲先拿锁检查Q，发现12还在，谓词已经为真，根本不进入等待，直接取出。没有等待者时，那次通知不会存起来；保存事实的是Q中的作业。
A: 像仓库里的货和门铃：货放在里面，门铃只是提醒。但这个比喻不能被理解成，门铃响一次就给某人一张取货票。
B: 更不能理解成程序可以像人一样，先放下钥匙，再慢慢决定睡觉。比喻解释提醒和状态的区别，检查、放锁、等待的原子协议仍得由程序认真实现。
> 来源：S07《Shared Memory IV》物理页9–10、12–13；WG21 N4659物理页1404–1405。竞争消费者、通知先到与门铃类比为自编解释，不引入信号量令牌语义。

## S06 — 接口要包住完整动作
A: 有些消费者不想等新订单，看到空队列就去做别的事。我能先调用empty，等它说不空，再调用pop吗？这两个方法各自加锁。
B: 仍然不够。empty结束时放了锁，pop开始时又拿一次锁，两者之间丙可以取走最后一份作业。每个小方法内部安全，不等于组合起来的业务动作安全。缺的是把判断与取出放进同一次持锁区间。
A: 所以应该提供try_pop，尝试取出：拿锁，如果空就报告没有；不空就读队首、删除，再报告成功。
B: 对。它不等待新作业到来，但取得mutex本身仍可能等待，不能因此叫它无锁或保证立即返回。wait_and_pop与它的区别在于，空时要不要等条件变化；同锁内完成检查、读取、删除这一点，两者一样。
B: 如果干脆绕开锁读取普通队列内部状态，还可能构成C++的数据竞争，data race，后果是未定义行为，不是我们能随便列几个错误输出的合法实验。取出的订单归当前工作流处理后，就释放队列锁，再做耗时处理，不要把整个排序过程包在队列临界区里。
> 来源：S07《Shared Memory IV》物理页12–13；C02-K03《条件变量与生产者消费者队列：从零讲解》的自编try_pop对照；《共享内存与GPU：来源澄清及模型边界》§1。try_pop为教学接口，未宣称工程实现完整。

## S09 — 练习一解析
A: 第一问的坏路径是：甲检查空并放锁；乙入队21并通知，但甲还不是等待者；通知没有被保留；甲随后才睡下。如果没有新的通知，这条路径就可能一直卡住，虽然Q里已经有21。
B: 修复不是要求生产者多通知几次，而是用正确的条件变量等待协议取代手工放锁再睡。甲持锁检查，用wait原子地释放锁并进入等待，醒后重新取得同一锁，再复查。生产者也在这把锁下修改Q，不能只给消费者加锁。
A: 第二问，两人都醒，不等于两份作业。假定甲先拿锁，看到21并取走；丙后拿锁时Q已空，谓词为假，就继续等待。交换甲丙的名字也一样。
B: 所以只回答要防伪唤醒还不完整。这道题的关键，是一次真实通知也不预留资源，消费者之间仍可能竞争。
A: 第三问，甲不需要第二次通知。第一次通知没有库存，但21还在Q里。甲持锁检查非空，带谓词wait可以直接继续，随后在同一持锁区间取出21。
B: 对照你的答案，检查四件事有没有讲全：放锁与进入等待不可手工拆开，醒后重新拿锁，拿锁后复查，以及状态由Q保存。只背一句要用while，没有解释这些因果，还不足以排查这个服务。
> 来源：自编EP04-A1；同步语义依据S07物理页9、12–13及WG21 N4659物理页1404–1405。

## S10 — 从队列状态到一份计算结果
A: 订单现在能安全取出了。接下来我要把一批订单按编号排序。队列以后还会一会儿空、一会儿不空；但这一批的排序，只要完成一次。我还需要不断检查队列吗？
B: 不需要。这里等的是这一批的结果，可以用future，未来结果句柄。把它想成通向某一次结果状态的读取端：状态起初尚未就绪，之后保存结果值，或者保存计算失败的异常。这份状态称为shared state，共享状态。
A: 谁来把结果放进去？future自己会计算吗？
B: 它不是计算引擎。若用promise，承诺对象，promise就是供应结果的一侧，future是读取的一侧。主流程先取得future，把promise交给负责计算的工作者；工作者算完设置值，共享状态变成就绪，等待结果的人才能继续。promise本身也不创建线程，谁来执行工作是另一项安排。
A: 如果工作者在我开始等待之前就把结果交了呢？
B: 结果保存在共享状态中，不会因为当时没人等就消失。你调用get时，若已经就绪就读取；若尚未就绪就等待。若里面存的是异常，get会把异常重新抛给读取方，而不是返回一个伪造的成功值。
A: 这里的get与条件变量的wait，听起来都能等，但前者认的是这一份结果，后者还要回到队列检查一个可能反复变化的条件。
B: 正是。普通future的get消费这一次读取资格，之后不能在同一份有效状态上反复get新订单。如果多个人需要读取同一批计算的结果，可以转换成shared_future，共享未来结果句柄，让读取方各持一份副本。它共享的是同一次完成，不会因此变成能反复装填的消息队列，也不会自动允许大家随便改结果对象。
B: 讲义还给了手动线程配promise的例子。别漏掉线程寿命：通过future取到值，不等于已经替你对手动创建的thread执行了join。
> 来源：S08《Shared Memory V》物理页4–6；WG21 N4659物理页1417–1420，[futures.unique_future]与[futures.shared_future]。promise与结果状态的作业服务解释为自编。

## S11 — 有结果句柄，不等于任务已经运行
A: 如果只是调用一个函数，拿到将来的结果，有没有比手动传promise更直接的写法？
B: std::async可以提交函数并返回future。但提交以后何时执行，要看启动策略，launch policy。指定launch async，任务按在另一个线程执行的方式启动；当前线程可以继续做独立工作。不过有另一个线程，并不等于两个核心此刻一定同时为你干活。
A: 另一种策略是deferred，延迟执行？
B: 对。它先保存函数和参数，不在后台偷偷算。第一次通过get或wait这种非定时等待操作要求完成时，才在调用那个等待操作的线程里执行。比如你先做自己的工作，再get，那么延迟任务是在get处才开始，而不是已经和你的工作重叠过了。
A: 如果我只写async，不写策略，它名字都叫异步了，总该默认异步吧？
B: 不能这样推断。省略策略时允许实现选择异步，也允许选择deferred。讲义后面的QuickSort示例恰好省略了策略。因此我们能讨论它允许的任务结构，却不能仅凭原样代码保证另开线程，或承诺固定加速。
A: 那我调用async以后，干脆不接住future，算不算把活扔出去就不用管？
B: 也不能当作fire-and-forget。若实际选了async，关联线程还没结束，而销毁这个future又释放了共享状态的最后一个引用，销毁就必须等该线程完成。没接住的临时future通常在所在完整表达式结束时销毁，比如一条调用语句的分号处，不是看代码写了几行。
B: 反过来，若选的是还没触发的deferred，直接丢弃future并不会替你执行任务。也不要概括成所有future析构都等结果。这里会明确保存future，直到需要结果的汇合位置。任务输入也要活到最后一次使用结束，异步不是逃开上一讲寿命规则的捷径。
> 来源：S08《Shared Memory V》物理页5、7、13；WG21 N4659物理页298，[class.temporary]/4；物理页1412，[futures.state]/5；物理页1420–1421，[futures.async]/1–5。采用C++17工作草案的明确语义，不把无策略调用当强制异步。

## S12 — 先把工作分开，再谈并行
B: 来到这一批订单。我们选择快速排序，QuickSort。先不急着开线程，要先保证分出来的工作真能独立执行。
A: 是不是让两个函数各拿一个输入，各自返回排好序的结果，避免都去改一张共享表？
B: 这就是这里的函数式编程风格，functional programming style。理想的纯函数只依赖参数，不读写隐藏的外部状态。在这个例子里，我们让左右任务分别拥有自己的子列表；等它们返回，再拼起来。这样更容易看清数据由谁负责，以及两边有没有共享写。
A: 那函数里面完全不能修改东西？
B: 不能把接口风格和内部实现混为一谈。讲义用按值传入的列表，并在内部移动、分区、重新连接节点，返回结果；它的接口是函数式风格，实现仍有为了效率而做的修改。关键是那些修改不能偷偷冲突到另一任务的数据。
B: 同样，写成lambda并不自动纯。如果它捕获同一个外部可变对象，两个任务仍可能冲突。也不能把数学上的理想函数，直接当成所有标准库数学例程都没有任何外部状态的保证。我们这里要掌握的是独立输入和依赖关系，不是用一个函数式标签代替访问检查。

## S13 — 一批订单怎样拆分

## S18 — 练习二解析
A: 正确依赖仍然是分区在前，两支独立，拼接在后。在真正异步的安排里，分区到第2毫秒结束。lower从第2毫秒到第9毫秒；higher从第2毫秒到第5毫秒。

B: 每次最小枢轴的变式，lower没有元素，higher承接几乎全部剩余元素。图不再有两条有分量的独立支路，而更像一条长链。future仍然能交付结果，只是不能替算法制造均衡的工作，也没有消除每层的顺序分区。

## S19 — 理想图以外的账
A: 两支分得均匀，又把get放对了，实际服务就一定更快吗？
