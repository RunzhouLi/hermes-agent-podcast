# EP04 学习附录 — 什么时候等待，什么时候继续做别的事？

## 2. 术语：用途、位置与边界

| 中文／英文 | 在作业服务中的意思 | 不应混淆的边界 |
|---|---|---|
| 队列／queue；抽象数据类型／ADT | 队尾入队、队首取出；Q保存尚未领取的订单 | 并发消费者开始处理和完成处理的顺序，不由FIFO容器单独保证 |
| head / tail | 讲义数组示意中的队首与队尾位置 | 环形索引、空满区分和容量协议本讲未实现；见附录A |
| 互斥锁／mutex | 把相关队列访问串成受保护的临界区 | 各调用各自用不同锁，不能保护同一共享队列 |
| 谓词／predicate | 一个真假检查；本例是`!Q.empty()` | 读的是被保护的实际状态，不是“我收到过通知” |
| 轮询／polling | 周期性重新查看状态 | 查得勤有无用工作，查得稀可能响应迟；不是通知协议的任意替代实现 |
| 条件变量／condition variable | 让线程等待，并由通知提供重新检查条件的机会 | 本身不保存订单、不累计通知票券，也不判断谓词一定成立 |
| `std::unique_lock<std::mutex>` | RAII锁所有权包装器；允许wait释放并重新取得锁 | 不把普通mutex变成递归锁；同一已持锁的unique_lock不能靠再次lock递归进入 |
| `notify_one` / `notify_all` | 通知一个／全部当时在该条件变量上等待的线程 | 不保留作业，不保证被唤醒者先取得mutex |
| 伪唤醒／spurious wakeup | 即使没有对应通知，也可能结束一次阻塞等待 | 即使完全没有伪唤醒，其他消费者先取走资源仍要求复查 |
| `wait_and_pop` / `try_pop` | 空时等待新作业／空时报告没有作业 | try_pop不等新作业，但取得mutex仍可能阻塞；不是lock-free保证 |
| 未来结果句柄／future | 某次异步供应结果的读取端，关联一个shared state | 不是线程或执行引擎；普通future的get不是反复取下一条消息 |
| 承诺对象／promise | 显式设置那一次结果或异常的供应侧 | 不自动创建工作线程；手动线程的完成与join仍须管理 |
| 共享未来结果句柄／shared_future | 可复制读取端，让多个读取方等待同一次完成 | 不是可反复重置的事件流；结果对象上的冲突修改不因“shared”而安全 |
| 启动策略／launch policy | 指定async或deferred等执行方式 | 有future不意味着任务已经在后台运行 |
| 延迟执行／deferred | 第一次非定时等待时，在调用等待操作的线程里执行已保存的工作 | 不是“现在就在后台慢慢算” |
| 快速排序／QuickSort；枢轴／pivot | 选枢轴，把其余数据分成子问题，再递归排序并拼接 | 子问题大小取决于数据和枢轴选择，不保证均衡 |
| 分区／partition | 把满足比较谓词的元素放在另一组元素之前 | `std::partition`不保证组内原有相对次序；不等同于稳定分区 |
| 函数式编程风格／functional programming style，FP style | 输入与返回结果清晰，尽量消除隐藏的共享写 | 局部命令式实现与FP式接口可以并存；lambda也可能有副作用 |

头文件识别即可：mutex及锁包装器来自`<mutex>`，条件变量来自`<condition_variable>`，future/promise/async来自`<future>`。本讲不要求背完整声明。[S06 p12；S07 p4、7–10、12–13；S08 p4–7、9–14；N4659 p1404–1405、1416–1421。]

## 3. 队列：状态才是记忆

### 3.1 本节模型

- Q是**无界教学队列**；本节只讨论入队、取出成功的正常路径。
- 每次对Q的检查和修改都用同一个mutex，m；同一条件变量上的消费者等待也使用该m。
- Q、m、条件变量以及任务所需数据都活到最后一次使用结束。条件变量的存在不能替代对象寿命协议。
- 持锁检查到非空之后，读取队首与删除队首仍在同一持锁区间；拿到订单后释放队列锁，再进行耗时处理。
- `wait(lk, pred)`可按`while (!pred()) wait(lk)`理解。普通wait会原子地释放锁并阻塞；醒后重新取得锁再返回。带谓词版本会再次检查，只有谓词为真才越过整个等待调用。[S07 p9、12–13；N4659 p1404–1405，[thread.condition.condvar]/9–18。]

### 3.2 自编状态表：作业12

“条件变量等待者”列不把“已经唤醒但尚在争mutex”混同成仍在条件变量上睡眠。

| 时刻／动作 | Q | mutex持有者 | 条件变量等待者 | 说明 |
|---|---|---|---|---|
| 甲持锁检查 | `[]` | 甲 | 无 | 谓词为假 |
| wait释放m并进入等待 | `[]` | 无 | 甲 | 释放与进入等待不可由调用方手工拆开 |
| 乙持锁入队 | `[12]` | 乙 | 甲 | Q保存作业 |
| 乙解锁，再notify_one | `[12]` | 无 | 甲已被唤醒 | 甲还没有自动取得m |
| 甲重新取得m | `[12]` | 甲 | 无 | 复查谓词为真 |
| 甲读取并删除 | `[]` | 甲 | 无 | 当前工作流取得12；读与删之间不放锁 |
| 甲离开临界区 | `[]` | 无 | 无 | 队列可供下一次操作 |

**改变调度：** 在甲被唤醒而尚未得锁时，丙先得锁取走12。甲后来拿锁看到空队列，必须继续wait。这个反例使用真实通知，不依赖伪唤醒。

**改变到达顺序：** 乙先入队并通知，当时无人等待。甲之后持锁见Q非空，直接取出，不需要补通知。保留下来的是12，不是通知。

**改变通知位置：** 乙也可以持锁改好Q后notify，再释放m。醒来的甲仍须取得m，因此这种顺序不因“尚未unlock”而非法。不能把S07 p9的一种演示顺序当成唯一正确次序，也不能把p13持锁notify本身列为错误。[S07 p9、13；N4659 p1404–1405。]

### 3.3 只表达同步关系的伪代码

以下是**正常成功路径的同步伪代码，不是可直接编译的C++容器模板**。它故意没有有界容量、关闭、取消、完整异常安全、拷贝构造和析构等待策略；这些不由几行wait自动补齐。

```text
共享成员：Q、mutex m、condition_variable cv

push(order):
    在 lock_guard(m) 的作用域内：
        Q.push(order)
    // 上述作用域结束，m已释放
    cv.notify_one()

wait_and_pop():
    lk = unique_lock(m)              // 现在持有m
    cv.wait(lk, predicate = !Q.empty())
    // 整个带谓词wait结束：持有m，且Q非空
    value = Q.front()
    Q.pop()                         // 此前没有释放m
    返回 value；退出作用域释放m

try_pop(out):
    在 lock_guard(m) 的作用域内：
        若 Q.empty()：返回 false
        out = Q.front()
        Q.pop()
        返回 true
```

错误组合是“单独加锁的empty，放锁，再调用单独加锁的pop”。中间另一消费者可以取走最后一项。接口应包住整个业务动作，而不是要求调用方拼凑多个过期观察。[S07 p12–13；自编C02-K03讲解。]

### 3.4 轮询与漏通知问题不要混淆

S07 p7–8的示例会解锁、睡100毫秒、重新加锁，再检查flag。**100毫秒是该页的示例参数，不是性能建议。** 在状态受同一锁保护且未来仍有检查的前提下，它可能发现后来到达的作业，只是增加无用查看或响应延迟。

T1a特意换成**只能靠通知唤醒的等待**：若检查后手动unlock，尚未正式成为等待者时通知已发生，随后才睡，就有错过这次通知的路径。不能把这种危险组合与正确的`cv.wait`等同。S07 p10“条件变量相对忙等的优化”只说明状态协议应是基础，不意味着任意拆散的unlock/sleep/lock都保有wait的原子语义。[S07 p7–10；N4659 p1404–1405。]

## 4. Future：一次共享结果，不是反复通知

### 4.1 三种职责

```text
执行安排：谁、何时运行计算？             thread / async的策略等
结果供应侧：把一次值或异常交给共享状态    promise（若显式使用）
读取侧：等待该状态就绪并取得结果          future / shared_future
```

手动promise路径的概念生命周期：

1. 创建promise，经`get_future()`取得对应future。
2. 把供应侧交给实际工作者；这一步与“安排工作者在哪个线程运行”分开。
3. 工作者完成后设置值；若选择传播失败，则显式存入异常。**不能把手动thread抛出的异常误认为会自动被promise捕获。**
4. 读取者先做不依赖该结果的工作；第一次需要结果时get。已经就绪可直接读取，未就绪则等待；若共享状态存的是异常，get会重新抛出。
5. 若显式创建了`std::thread`，仍须安排join与所有退出路径的寿命管理。get到值不等于对手动thread执行join。[S08 p4–6；N4659 p1414、1417。]

`std::async`能代为安排函数调用并返回future；该调用返回的值或抛出的异常由其机制存入共享状态。不要把这种自动捕获行为推广到任意手动thread/promise组合。[S08 p5、7；N4659 p1420–1421。]

| 对象／操作 | 结果就绪之前 | 结果就绪之后 | 限制 |
|---|---|---|---|
| 普通`future<T>::get()` | 等待这一次结果 | 取得值或重新抛出存储的异常 | 调用后future不再关联该共享状态，不能拿它再get下一条消息 |
| `future::wait()` | 等待就绪 | 返回就绪事实 | 与get不同，不负责取走结果；deferred时非定时等待会触发执行 |
| `shared_future<T>` | 多个读取端可等待同一状态 | 各读取方可读取同一结果 | 仍是同一次供应；通常让各线程持自己的副本，不能据此任意并发修改句柄或结果 |
| 条件变量＋Q的谓词 | 谓词假时释放mutex并等待 | 重获mutex后重新判断Q | Q可反复空／非空；通知本身不保存值 |

普通`shared_future<T>::get()`返回共享状态中值的const引用；引用使用还必须满足共享状态寿命，且不引入数据竞争。这里只识别这个边界，不展开引用特化或并发可变结果的设计。[S08 p4；N4659 p1416–1420。]

### 4.2 启动策略与隐藏的等待

| 调用的策略含义 | 何时执行函数 | 能否只据这个句柄断言两个核心重叠 |
|---|---|---|
| 显式`std::launch::async` | 按在另一执行线程中调用函数的方式启动 | 不能；还需核心、调度、工作独立性等条件 |
| 显式`std::launch::deferred` | 第一次非定时等待，如get或wait，在调用该等待操作的线程内执行 | 不能；此前没有后台执行 |
| 不写策略的`std::async(f, args...)` | C++17语义等价于允许async或deferred，由实现选择 | 不能保证真正异步 |

“第一次非定时等待”不要随意改成“任意询问状态”。定时等待接口在deferred状态下不会像get那样开始该延迟函数；完整超时接口用法本讲延后。[N4659 p1417、1420–1421。]

保留future直到汇合位置，并保持任务输入的有效寿命。区分三种情况：

- **实际采用async：** 若关联线程尚未完成，销毁future又释放了共享状态的最后一个引用，该释放返回之前必须等到关联线程完成；不是每销毁一个shared_future副本都等待。
- **仍未触发的deferred：** 没有任何非定时等待触发它，直接释放最后一个结果句柄不会替你调用该延迟函数，任务可以根本不执行。
- **promise等其他来源：** 释放结果句柄没有上述“等待async关联线程完成”的义务；不能把所有future析构都说成等结果。[N4659 p1412，[futures.state]/5；p1420–1421，[futures.async]/3–5。]

没接住的临时future通常在所在**完整表达式结束**时销毁，例如独立调用语句的分号处；不是以源码换行为界。因此丢弃临时future不能当作fire-and-forget，既可能挡住下一条语句，也可能因deferred从未触发而根本不执行工作。[S08 p13；N4659 p298，[class.temporary]/4；p1421，[futures.async]/3–5。]

## 5. QuickSort：把算法依赖与代码先后分开

### 5.1 原图与自编例的关系

S08 p10《FP-style QuickSort / 1》的原图从左侧列表出发，围绕枢轴分成上下两支，继续递归拆分，在右侧把各子结果接回。它展示拆分和汇合，不是某次实机调度记录。原图使用较长的输入；以下五元素例是为了可听手推另行编写，**不是原图数字的逐项转录**。[S08 p10。]

自编输入：`[5, 2, 8, 1, 7]`，第一个元素5作pivot。

| 层次 | 枢轴 | 本次选定的lower分组表示 | 本次选定的higher分组表示 | 返回 |
|---|---:|---|---|---|
| 顶层 | 5 | `[2, 1]` | `[8, 7]` | `[1, 2, 5, 7, 8]` |
| lower子问题 | 2 | `[1]` | `[]` | `[1, 2]` |
| higher子问题 | 8 | `[7]` | `[]` | `[7, 8]` |

拼接正确需要同时满足：

- lower、higher内部各自排序正确；
- 所有lower元素小于pivot，所有higher元素不小于pivot；
- 每个输入元素归入且仅归入一个位置，pivot也保留一次。

等于pivot的元素按这里的`<`比较归入higher。空列表与单元素是递归的简单边界。以上组内排列只是选定的一次手推表示；`std::partition`只保证满足谓词的元素在不满足者之前，**不保证组内保持原相对次序**。不要把它当成`stable_partition`。[S08 p11–13；N4659 p1050–1051，[alg.partitions]。]

### 5.2 依赖图

```text
                        lower排序 ──────┐
分区（顺序） ──────────┤                ├── 拼接(lower结果, pivot, higher结果)
                        higher排序 ─────┘
```

文字精确读法：分区分别指向lower和higher；lower与higher分别指向拼接。**lower与higher之间没有由这个算法的数据需求强制形成的箭头**，但前提是它们拥有独立数据，比较逻辑没有隐藏的冲突访问。[S08 p9–14。]

S08 p11先给顺序版；p12延续同一版、突出两次递归调用的位置；p13将lower改为async并用future汇合。不要把三页当成三个不相关的排序算法。

### 5.3 只表达调度关系的伪代码

```text
先分区，得到归各自任务拥有的lower、higher和单独的pivot

保留重叠的结构（此处明确指定async）：
    lower_future = async(launch::async, sort, move(lower))
    higher_result = sort(move(higher))
    lower_result = lower_future.get()
    返回 concatenate(lower_result, pivot, higher_result)

过早等待的结构：
    lower_future = async(launch::async, sort, move(lower))
    lower_result = lower_future.get()       // 当前线程在独立higher开工前就等
    higher_result = sort(move(higher))
    返回 concatenate(lower_result, pivot, higher_result)
```

这是调度伪代码，不是已编译的递归任务库。实际课程p13没有显式写出`launch::async`；本附录为解释时间模型**主动添加并标明了这项前提**。保存future到汇合、正确转移输入所有权与保持引用寿命，是另外的义务；单写`move`不自动证明任务没有外部别名或悬空引用。[S08 p11–14；N4659 p1420–1421。]

### 5.4 自编时间账本

把左右各自整段排序视为时长已经给定的两个任务，不再对每层递归的内部线程调度建模。设：

- P：顺序分区时间；L：lower整段工作时间；H：higher整段工作时间；M：最后拼接时间。
- 两个可用核心，明确且实际异步，两支可在分区完成后同时开始；没有任务创建、调度、数据传递等额外开销，没有隐藏依赖。

则：

```text
先重叠再get：T = P + max(L, H) + M
立即get后才做higher：T = P + L + H + M
先做higher、再get触发deferred的lower：T = P + H + L + M
重叠安排中get的剩余等待：max(L - H, 0)
```

本讲演示取`P=3ms, L=4ms, H=6ms, M=1ms`：

| 工作 | 先重叠后get | 立即get |
|---|---|---|
| 分区 | 0–3ms | 0–3ms |
| lower | 3–7ms | 3–7ms |
| 当前线程的higher | 3–9ms | 7–13ms |
| get位置与等待 | 第9ms读取，剩余等待0ms | 第3ms等待到第7ms |
| 拼接 | 9–10ms | 13–14ms |
| 总时间 | `3+max(4,6)+1=10ms` | `3+4+6+1=14ms` |

上述都是模型算式，并非“对默认async代码测到10ms”。顺序分区和最后拼接仍然存在；两支并不使整段程序自动快一倍。[自编C02-K04讲解；S08 p7、13–14。]

## 6. 练习一：队列协议

**先答题。音频题面S07，可选提示S08，解析S09。** 每小问独立重新设定场景。

### 题面

- **T1a／O1：** Q初始空。甲持锁检查后手动unlock，准备进入只能靠通知唤醒的等待。乙恰在甲解锁后、正式成为等待者前，持同一mutex入队21，解锁并notify；以后没有新通知。画一条可能卡住的路径，指出应替换什么步骤。不是定期自动醒来的轮询。
- **T1b／O2：** 甲、丙都在条件变量上等待，乙只放入一份21却notify_all。两人能否醒后都不复查就直接取？分别写出先后拿锁时Q的状态。
- **T1c／O2：** 乙先入队21并通知，当时无人等待，也没人取走。甲之后才来，正确的带谓词wait是否还需第二次通知？解释到底谁记住了什么。

### 可选提示

a：把检查、放锁、进入等待分成格子，看生产者能插在哪里。b：醒了以后仍须竞争mutex。c：先执行谓词检查，后决定是否阻塞。

### 推理答案

**T1a：** 甲检查空→手动解锁→乙入队21并通知，但甲尚未等待→通知不被保存→甲随后才睡下。存在之后一直未被唤醒的路径，不能靠队列里已经有21让错误睡眠自动修好。正确修复为：持同一mutex检查谓词；假时由`cv.wait`原子地释放锁并进入等待；醒后重获同一mutex并复查；真时在同一持锁区间读并删。生产者同样持这把锁修改Q。不要靠“多发几次通知”修补窗口。

**T1b：** 不可以。若甲先得锁，见`[21]`并取走；丙后来得锁，见`[]`，应继续wait。通知并不分配一份订单给每个醒者。该反例无需任何伪唤醒；仅回答“因为可能伪唤醒”没有抓住本题的资源竞争。

**T1c：** 不需要第二次通知。甲持锁看到Q含21，谓词真，不进入阻塞，直接取出。状态保存在Q；旧notify没有被条件变量积存。

**自测判据：** a须有窗口、同一mutex、wait原子释放/等待、重获锁；b须有醒后竞争与复查；c须明确Q保存状态而非通知保留名额。`try_pop`的延伸边界：检查与取出也必须合并为一次持锁动作，并且“不等新作业”不等于“取得mutex绝不等待”。

这些是自设学习判据，不是官方评分细则。[依据S07 p9–10、12–13与N4659 p1404–1405的自编T1/A1。]

## 7. 练习二：任务图、策略和时间

**先暂停画图。音频题面S16，可选提示S17，解析S18。**

### 题面

新批次：`P=2ms, L=7ms, H=3ms, M=1ms`。先假设两个可用核心、明确异步、两支能同时开始、没有额外开销。

1. 画出分区、lower、higher、拼接的依赖边。提交lower后先做higher再get，总时间多少？来到get时lower还剩多久？
2. 若提交lower立即get，之后才做higher，总时间多少？哪一条顺序是代码人为加入的？
3. 若未指定启动策略，运行库选deferred，第一种代码结构仍保证重叠吗？按相同无开销模型算时间，并写出lower从何时、在哪个线程开始。
4. 假定每次pivot都是当前子问题的最小元素，左右工作量和任务图怎样变化？future是否因此失去结果交付能力？
5. 服务中的Q反复变空，而这一批lower只交付一次结果。两处分别等待什么？手动连接promise与future时，谁交付、谁在何处读取？

### 可选提示

分区完成才有两支输入；lower与higher之间不要凭代码行序画数据依赖。标出higher结束的时刻，再看lower是否结束。deferred先问何时开工，再选公式。最小pivot时，数一数lower有几项。

### 推理答案

**1．先重叠再get：** 分区0–2ms；lower为2–9ms；higher为2–5ms。当前线程第5ms来到get，等待4ms，至第9ms汇合；拼接9–10ms。

`T = 2 + max(7,3) + 1 = 10ms`，剩余等待`7-3=4ms`。晚get仍可能等待；它保证的是不先放弃可做的独立higher，而不是保证get绝不阻塞。

**2．立即get：** 分区0–2ms；lower为2–9ms；higher推迟到9–12ms；拼接12–13ms。

`T = 2 + 7 + 3 + 1 = 13ms`。人为加入的是“lower完成以后，higher才开始”；排序算法本身并不需要这条左右之间的先后边。

**3．deferred：** 不保证重叠。当前线程先完成分区0–2ms、higher 2–5ms；第5ms的get才在该线程内开始lower，执行到第12ms；拼接到第13ms。

`T = 2 + 3 + 7 + 1 = 13ms`。同样是13ms，但失去重叠的原因是启动策略，不是把get放在higher之前。省略策略不能提供固定加速承诺。

**4．最小pivot：** 对非空子问题，lower为空，higher容纳除pivot外几乎所有剩余元素。可利用的左右并行趋向消失，递归图更像长链；每层仍需顺序分区。future仍可供应和等待结果，只是不创造工作平衡、不消除计算量。

**5．两类等待：** 队列端按同一mutex反复检查`!Q.empty()`，通过条件变量等待变化；排序端等待这个lower对应的future共享状态就绪。手动供应侧由工作者用promise设置结果，读取侧在拼接真正需要lower前get，中间先做独立higher。future/promise本身不是线程创建保证；输入与结果句柄寿命仍须正确。

**O3判据：** 必须区分一次结果和反复条件、结果供应与读取职责、默认策略与deferred，不把future当“已开新线程”的凭证。

**O4判据：** 必须有正确依赖边、模型条件、10ms与13ms及4ms的推导、get位置、顺序分区和最小pivot失衡原因。只有两个总时间数字而没有因果，不满足学习目标。[依据S08 p4–7、10–14与N4659 p1420–1421的自编T2/A2。]

| 源页 | 容易出现的误读 | 本讲采用的澄清 |
|---|---|---|
| S06 p12 | unique_lock的功能表意味着它能让普通mutex递归加锁 | 包装器管理所有权；底层mutex是否支持递归是另一回事 |
| S07 p9与p13 | 只有先unlock后notify才合法 | 两种通知位置都可能正确；同锁状态协议、重获锁与复查不可省略 |

即使没有普通data race，也可能有把empty与pop分开导致的业务竞争；若普通共享访问已经存在data race，则C++行为未定义，不能以运行几次、碰巧得到某些输出作为正确性证明。队列、锁、条件变量及异步输入的寿命也不能由“加了锁”自动延长。[《共享内存与GPU：来源澄清及模型边界》§1–2；EP03先修。]
