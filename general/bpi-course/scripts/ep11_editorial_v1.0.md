# EP11 — 事件数据与探索（Event Data & Exploration）

A: 我先抛个问题，咱们这门课已经走过十集了。前四种发现算法——Alpha 数关系、Heuristic 数频率、Region 画状态图、Inductive 切蛋糕——我都跟下来了。可是有件事我越想越虚。

B: 你说。

A: 这四种算法，吃进去的都是同一样东西——事件日志，English 叫 event log。我们一直把它当成桌上摆好的一盘菜，拿起来就分析。可这盘菜……到底是谁做的？它是被"给"的，还是被"造"出来的？

B: 这就是今天整集要回答的问题。我先把答案的轮廓给你：事件日志几乎从来不是被"给"的，它是被"造"出来的——从一堆原始系统里抽取、挑选、塑形出来的。而每一个"造"的动作，都有代价。

A: 等一下，这听着有点反直觉。我一直以为系统里就躺着一份现成的日志，导出来就行。

B: 大多数人都这么以为，这正是今天要打破的第一个错觉。我给你换个画面——你想象一下石油勘探。

A: 石油勘探？钻井那个？

B: 对。一片地底下有没有油、油在哪一层、值不值得钻，地质学家不会直接拿到一桶油。他们面对的是一整片地质构造——岩层、断层、孔隙。他们要先勘探、再选点、再钻取、最后还得净化原油。事件数据，就是这片地质构造。

A: 哦——所以日志不是那桶现成的油，是地底下那片还没动过的岩层？

B: 正是。整集你都可以用这个画面来锚定。今天我们要走六件事。第一，事件日志的元模型——这是岩石的分类系统，你得先认识你脚下是什么岩。第二，点图，英文是 dotted chart——这是地震勘探，钻之前先看清地下的纹理。第三，事件从数据库里怎么抽出来——油从地里怎么取。第四，也是今天的核心——案例概念，English 是 case notion，你到底要钻进哪一层。第五，对象中心数据，你会发现地层是相互重叠的。第六，数据质量和记录指南，怎么不让自己在错的地图上瞎钻。

A: 六件事，一条线：认岩、勘探、取油、选层、看清重叠、别钻错。我喜欢这个排法。那从认岩开始？

B: 从认岩开始。我们先回到最朴素的问题——一个事件（event），到底是什么。

A: 这个我有把握。我脑子里的事件日志，就是一张大表。每一行是一条记录，有订单号、有干了啥、有时间。

B: 你说得没错，这正是教材里叫"简单视图"（simplistic view）的那张表。我把一段念给你听你感受一下：订单 9901，register order，2014 年 1 月 22 号上午 9 点 15；9901，check stock，9 点 49；9901，ship order，10 点 11；9901，handle payment，10 点 41。

A: 嗯，一眼就懂。订单号、活动名、时间戳，后面可能还挂点别的——谁干的、什么产品、几件。

B: 对，那张表里其实藏着四类东西：case id（案例号），activity name（活动名），timestamp（时间戳），还有 resource（资源，比如 Sara Jones、Pete Scott 这些人）和其它数据。问题是——这张表太"扁"了。它把很多层次压成了一行，方便看，但骗了你。

A: 骗了我？哪里骗了？

B: 你看,"register order"这五个字，在表里出现了好几次,对吧?9901 一次、9902 一次、9903 一次。

A: 对，三次。

A: 等一下，我好像懂你要说什么了。这三次"register order"，是同一个"动作"，还是三个不同的动作？

B: 你自己说说看。

A: 应该是……同一种动作，但发生了三回？就像"刷牙"这件事，我今天早上刷、晚上刷，是两次刷牙，但都叫刷牙。

B: 这就是今天第一个必须分清的区别。教材给它一个更精细的视图（a more refined view）。我给你搭一个层级，你跟着想。最顶上是流程（process）。一个流程底下有很多案例（case），每个 case 就是一次完整的走完——一张订单从头到尾。

A: 流程是"订单处理"这件事本身，case 是某一张具体订单走的那一遍。

B: 对。再往下，每个 case 由若干活动（activity）组成。但注意，这里 activity 是"类型"。然后是活动实例，English 叫 activity instance——这是这个类型的一次具体执行。最底下才是事件（event）。

A: 所以"刷牙"是 activity 类型，"今天早上那次刷牙"是 activity instance。

B: 完全是这个意思。一个"check ticket"活动类型，可以有成千上万个实例，每个实例是某张票被检查的那一回。

A: 那 event 又是什么？它和 activity instance 不一样吗？

B: 这是关键。一个 activity instance 常常不是一瞬间的，它有持续时间。所以一次执行里，可能记录好几个 event——开始一个、结束一个。event 是最细的颗粒，是某个时刻打下的一个戳。

A: 哦，所以层级是：流程 → 案例 → 活动类型 → 活动实例 → 事件。从大到小五层。

B: 对。而且每个 event 身上挂着属性（attribute）。有三个属性教材特别强调。第一个，timestamp，时间戳——它决定事件的先后顺序，也是性能分析的命根子。第二个，resource，资源——执行这个事件的人、机器、部门或组织，分析瓶颈和组织协作全靠它。第三个，transactional information，事务信息——比如开始、挂起、完成，因为活动往往不是原子的。

A: 回到我们的岩层比喻——这个元模型，是不是就相当于地质学家的岩石分类系统？火成岩、沉积岩、变质岩那一套？

B: 你接得很准这个比喻。地质学家面对一块石头，第一件事是分类——这是什么岩、什么成因、什么颗粒度。你面对一条记录，第一件事也是分清层级——这是流程、案例、活动类型、实例，还是一个事件？分类错了，后面全错。

A: 那我们盯一下那个"事务信息"。你说活动不是原子的，有开始有结束。这背后是不是有一套状态？

B: 有，而且是今天第一个需要在脑子里画出来的图——事务生命周期（transactional lifecycle）。我口头给你走一遍，你跟着画。

A: 来，我闭眼想。

B: 一个活动诞生，第一步是 schedule，被排上日程。然后 assign，被指派给某个资源。指派完可以 reassign，改派给别人。

A: 排日程、指派、改派。还没真正开始干。

B: 对，到这都还没动手。接着 start，开始执行。执行中可以 suspend，挂起——人被叫走了、等材料了。挂起之后 resume，恢复。最后 complete，完成。这是顺利的主线。

A: schedule、assign、（reassign）、start、suspend、resume、complete。一条活动从排期到收工的全过程。

B: 但人生不总顺利。还有几条岔路。autoskip 和 manualskip——这个活动被跳过了，自动跳或人工跳。withdraw——撤回。abort_activity——中止这个活动。abort_case——整个案例都崩了。所以终态分两种：successful termination，成功结束；unsuccessful termination，失败收场。

A: 我重述一遍确认。主线是排期到完成，中间能挂起恢复；旁边有跳过、撤回、中止活动、中止整个案例，最后要么成功要么失败。

B: 就是这张图。现在有意思的来了——同一张图，不同的活动只走其中一段。教材给了几个实例。最简单的，schedule、assign、start、complete，规规矩矩走完。复杂一点的，schedule、assign、reassign、start、suspend、resume、complete，中间改了派、还挂起恢复过。还有的只有 start、complete，更原子。

A: 所以这张状态图是"全集"，每个真实的活动实例只是从里面挑一条路径走。

B: 对。而这就引出一个非常微妙、但极其重要的坑。我先给你制造点困惑。假设日志里，对同一个活动，连着记了：start、start、complete、complete。

A: 两个 start，两个 complete……等等，这是两次执行交叠在一起了？

B: 你来判断。这四个事件，怎么配对？

A: 呃……第一个 start 配第一个 complete，第二个 start 配第二个 complete？这是先进先出。还是说，第一个 start 配第二个 complete，第二个 start 配第一个 complete？这是嵌套。

B: 你看，你一下就说出了两种合理的配法，而且两种配出来的活动实例时长完全不同。教材里那个例子，一种配法是 5 小时和 6 小时，另一种配法是 9 小时和 2 小时。

A: 同样四个事件，谁配谁不确定，算出来的时长能差出快一倍。这太要命了。

B: 这正是"可能的混淆"（possible confusion）。教材说，解决办法有两条。第一，事件显式地指明它属于哪个活动实例——记录的时候就写清楚"我是第 2 次执行的开始"。第二，在回放的时候用启发式去推算、去配对。

A: 第一条是源头治理，第二条是事后补救。

B: 对。而这又回到我们刚才分清的那个区别——活动类型 vs 活动实例。如果你只知道类型,不知道实例,这种配对的歧义就永远甩不掉。

A: 所以"活动实例"不是一个学术上的吹毛求疵，它直接决定你算出来的时长对不对。

B: 一点没错。每个 event 都引用一个活动（这叫 classifier，分类器），通常作为属性显式给出。这是 event 和 activity instance 之间的桥。

A: 我顺一下属性这块。你前面说 event 有时间戳、资源、事务信息。属性是不是只挂在 event 上？

B: 不止。属性也可以挂在案例层（case level），甚至是算出来的。比如客户类型是金牌还是银牌，这是 case 级的；病人的出生日期，case 级的；还有整个案例的流转时间（flow time），这是算出来的派生属性。

A: 金牌银牌这种贴在整张订单上，不是贴在某个事件上。出生日期也是人的属性，不是某次挂号的属性。

B: 对。而且还有一类更外围的——上下文（context）。教材专门讲了"通过添加上下文来丰富事件数据"。案例和事件不能孤立地看。

A: 怎么个不孤立法？

B: 比如，此刻有多少个案例在排队等着、有多少资源空着、当天的天气、整体的工作负载。这些都会影响一个具体案例怎么走、堵在哪。教材把上下文分了四层：实例上下文，比如订单大小、客户类型；流程上下文，比如有多少资源、多少案例在跑；社会上下文，比如不同流程间的优先级、社交网络、压力、内部竞争；外部上下文，比如天气、经济、季节、法规变化。

A: 越往外圈，范围越大，但和"为什么这个案例堵了"的因果关系也越间接。

B: 你抓住了那张图的精髓——往外扩，覆盖更多实例、更多流程，但因果链也变长。这些上下文可以算出来或取回来，作为派生属性显式加进去。等我们后面讲到和机器学习的结合，它会扮演关键角色。

A: 好，那这一整套——五层级、属性、事务生命周期、上下文——有没有一个工业标准把它固定下来？

B: 有，这就是我们今天第一个必须按顺序记住的术语。整套案例中心的元模型，被一个叫 XES 的标准采纳了。英文是 eXtensible Event Stream，它现在的正式身份是 IEEE 1849-2023。

A: IEEE 标准，听着挺正式。它有多老？

B: XES 的开发 2009 年就开始了，2016 年成为正式 IEEE 标准，2023 年又更新续命了十年。它的结构就是我们刚说的：log（日志）→ trace（轨迹）→ event（事件）→ attribute（属性）。它还提供各种扩展，比如记录成本信息、软件日志等等。

A: 等一下，trace 和我们前面说的 case 是一回事吗？

B: 几乎可以这么用。case 是概念上的"案例"，trace 是它在日志里的落地形式——属于同一个案例的那一串事件的序列。这就是今天第二个术语：案例是 Case，而它在日志里留下的那串脚印叫轨迹 Trace。

A: 我把第一段收个尾。事件日志在结构上是五层：流程、案例、活动类型、活动实例、事件；每个事件挂着时间戳、资源、事务信息这些属性；活动不是原子的，有一整套生命周期；类型和实例必须分清，否则连时长都算不对；这一切被 XES，也就是 IEEE 1849-2023 固定下来。这就是我们的岩石分类系统。

B: 岩认完了。下一步——

A: 下一步该地震勘探了吧？钻之前先看清地下纹理。

B: 正是。这就是点图，英文叫 dotted chart。

A: 在我们这门课里,点图是个新东西吗?它算发现算法吗?

B: 这是第一个要纠正的误解——点图不是挖掘算法，它是探索（exploration）。你想，地质学家做地震勘探，不是去钻油，是去"看"——发一组震波下去，看反射回来的纹理，心里先有个数。点图就是这个动作。挖掘算法是钻头，点图是震波。

A: 所以它不产出模型，它让我看清数据长什么样。那它具体怎么"看"？

B: 主意特别朴素，朴素到优雅。教材说，点图是一个"直升机视角"（helicopter view），把所有事件一次性铺开。核心规则只有一条：每一个事件，对应图上的一个点。事件和点是一一对应。

A: 一个事件一个点。那点摆在哪由什么决定？

B: 这就是它的设计。横坐标 X，用事件的时间戳来算——可以是绝对时间、相对时间、逻辑时间等等。纵坐标 Y，用另一个属性，比如案例。然后点还能上色，按某个属性，比如资源或者活动名。

A: 等一下，我自己推一下。如果 Y 轴是案例、X 轴是绝对时间，那每一行就是一个案例，一行点从左到右铺开，就是这个案例随时间发生的一串事件？

B: 你推对了。这就是第一种视图：case id / 绝对时间。每一行是一个案例，点的颜色是活动。你能从中看出什么？

A: 我想想……如果某一段时间，很多行的左端点都挤在一起，是不是说明那段时间涌进来一大批案例？

B: 这就是点图最值钱的地方——它一眼暴露到达率（arrival rate）。一片密集的起点，是一波涌入。还有季节性、批处理。比如你看到点一柱一柱地竖着出现，那是批处理——一批活动被攒着一起干。

A: 那如果我换 Y 轴呢？比如 Y 轴放活动？

B: 那就是第二种视图：活动 / 绝对时间。每一行是一种活动，你能看到某个活动在时间上的分布——是均匀发生，还是集中在某些时段爆发。第三种，Y 轴放资源——资源 / 绝对时间。每一行是一个人或一台机器，你能看到谁在什么时候忙、谁在闲。

A: 三种视图，其实就是同一堆点，换三种方式摞起来：按案例摞、按活动摞、按资源摞。

B: 对，换三种纵轴。颜色还能再叠一层信息——按活动上色，或者按资源上色。同一张图，颜色一换，看到的故事就不一样。

A: 你前面提到 X 轴还能用"相对时间"。绝对我懂了，相对是啥意思？

B: 这是个特别巧的招。绝对时间是真实日历时间，1 月 22 号、2 月 3 号。相对时间（relative time）是——把所有案例都拉到同一个起跑线，让每个案例都从时间 0 开始。

A: 哦！这样的话……所有案例的起点对齐了，我就能直接比谁走得快、谁走得慢？

B: 你立刻抓到了用途。绝对时间回答"什么时候发生"，相对时间回答"花了多久"。把起点归零，案例的持续时间就能直接横向对比——这条案例 3 天走完，那条拖了 3 周，一目了然。

A: 这就像地震勘探里，你既能看"这片构造的真实埋深"，也能把几个构造叠在一起比"哪个孔隙发育得更好"。

B: 比喻贴。教材还顺带提了一个更细的工具,叫性能谱（Performance Spectrum），Celonis 里也有。

A: 它和点图什么关系？

B: 点图是每个事件一个点。性能谱更细，它盯的是"段"——从一个活动到下一个活动这一段，每一段的时间是怎么分布的。比绝对的点图能看出更细腻的性能纹理。这是 Denisov、Fahland 和 van der Aalst 2018 年在 BPM 会议上的工作。我们今天点到为止，知道有这么个更精细的镜头就行。

A: 那我收一下点图这段。点图是探索不是挖掘，钻之前的震波勘探；一个事件一个点，X 轴是时间、Y 轴是案例或活动或资源、颜色再叠一层；绝对时间看到达率和批处理，相对时间比案例时长；更细的有性能谱。

B: 但教材在这里冷不丁甩了一句话——"Not so simple"，没那么简单。

A: 哦？哪里不简单了？我们不是震波也发了、纹理也看了？

B: 问题是——我们这一路，都假设那桶油、那张点图，是现成的。可它从哪来？我们到现在都没回答：这些点，这些事件，最初是从哪个系统里冒出来的？

A: ……对啊。我又把它当成桌上的菜了。它到底从哪来？

B: 这就是第三段。从这里开始，比喻要往下钻了——我们要去地里真的取油了。

A: 取油。来。事件数据到底藏在哪？

B: 到处都是，又哪都不直接。教材列了一堆来源：医院里的数据库系统、CSV 文件或电子表格、交易系统的事务日志、SAP 或 Oracle 这种 ERP 商业套件、IBM 中间件的消息日志、还有从网站或社交媒体取数的开放 API。

A: 来源这么多，那不是挺好取的吗？

B: 这就是陷阱所在。教材紧接着一句"But……"——但是，绝大多数信息系统，根本不显式地存储或导出事件数据。

A: 等一下。这句话我得消化一下。你是说，系统里压根没有"事件"这种东西躺着？

B: 大多数时候，没有。系统记的是状态、是数据、是表。一个典型的 SAP 安装，有几万张表。一家医院，轻轻松松上千张和病人相关的表。你得先理解底下的数据模型，才能圈定、挑选出事件数据。

A: 几万张表……所以"取油"第一难，是你站在一片地上，根本不知道油在哪口井下面。

B: 这个画面准。地质学家面对一整片地，不是每个点都有油，他得先读懂地质构造。你面对几万张表，事件数据是要从里面"重建"出来的，不是导出来的。

A: 那怎么重建？总有套路吧。

B: 有。教材给了三种典型情况——这是很实用的方法论，你记住这三种，现实里九成的抽取都能对上号。

A: 我先猜一种。最理想的，是不是有张表，一行就是一个事件，带时间戳？

B: 你猜中了最理想的第一种。有些系统就有这种表或事务日志，每一行就指一个事件，自带时间戳——工作流系统的日志、机器日志就是这样。一行一事件，捡现成的。

A: 那第二种？

B: 第二种常见得多，也麻烦。很多系统的表，一行里有好几列都是时间戳。比如一行里有：提交日期、审核日期、接受日期、拒绝日期。

A: 哦……所以一行其实塞了好几个事件？提交是一个事件、审核是一个事件……

B: 对。一行代表好几个事件。而且那些没发生的，对应的列是空值（null）。比如这一行被接受了，那"拒绝日期"就是空的，意味着"拒绝"这个事件没发生。你得把一行"炸"成多个事件。

A: 这就像一块岩芯样本，一根管子里其实叠着好几层，你得自己切开数。那第三种？

B: 第三种是最高级的系统才有的——专门记录"表里发生了什么变化"的表。变更表（change tables）、重做日志（redo logs）。它不存状态，它存"这条记录从旧值变成了新值"。

A: 这个我得想一下。它记的是"差异"？

B: 对，记的是状态之间的差异（diff）。最典型的就是 SAP 的两张变更表：CDHDR 和 CDPOS。CDHDR 是变更文档头（Change Document Header），记高层信息——谁在什么时候做的改动、是哪个 SAP 事务、改了哪个文档。CDPOS 是变更文档项（Change Document Items），记细节——哪个字段、旧值是什么、新值是什么。

A: 所以你拿着"字段 X 从 A 变成了 B，是张三在 3 点改的"，反推出"哦，这是一个事件"。

B: 正是。从状态的变化，重建出事件。这三种——一行一事件、一行多事件、变更表——就是从数据库里找事件的三把铲子。

A: 我把这三种铲子复述一遍：第一，事务日志，一行一事件，最理想；第二，多列时间戳，一行炸成多个事件，注意空值是缺席的事件；第三，变更表比如 SAP 的 CDHDR 和 CDPOS，从状态差异里重建事件。

B: 但现在，真正的硬骨头来了。也是今天整集最重要的一刻。我先给你立个场景。

A: 来，我准备好了。

B: 教材给了一个订票系统的数据库。我口头给你描出这片地的构造，你跟着在脑子里连线。中心有几个实体。乐队（band），它办演唱会（concert）。演唱会在某个音乐厅（concert hall）举行。音乐厅里有座位（seat）。

A: 乐队、演唱会、音乐厅、座位。一条物理的线：谁演、在哪演、坐哪。

B: 对。另一条线是交易。客户（customer）下预订（booking）。一个预订包含若干张票（ticket）。每张票对应一个座位、一场演唱会。还有支付（payment）。

A: 客户、预订、票、支付。一条交易的线。两条线在"票"这里交汇——票既连座位演唱会，又连预订。

B: 你把这片构造读对了。而且这些关系不是一对一的。一个乐队 0 到多场演唱会，一个预订 1 到多张票，一个客户 0 到多个预订。还有些额外约束，比如同一个座位同一场演唱会不能出两张票，一个预订的总价等于各票价之和。

A: 关系密密麻麻。那……要从这片构造里做出一份事件日志，我得干嘛？

B: 你得做一个映射（mapping）——把这片数据库构造，映射到我们前面那个案例中心的元模型上去。而映射的第一步，也是决定性的一步，是回答一个问题。

A: 什么问题？

B: 什么是流程实例？换句话说，什么是一个"案例"？

A: 案例……不就是订单号那种东西吗？数据库里有个 ID 当案例号不就行了？

B: 那你告诉我，在这片构造里，案例应该是谁？教材直接把候选列了一排：票？预订？乐队？演唱会？音乐厅？座位？客户？还是支付？

A: ……呃。等一下。这些都能当案例？

B: 你来想。如果你选"票"当案例，会发生什么？

A: 如果票是案例……那每张票走它自己的一生：被预订、对应某座位、被支付。每张票一条轨迹。

B: 对。教材就问了——那票的生命周期里，活动是什么？而且有个麻烦：多个流程实例可能共享同一个预订事件或支付事件。因为一个预订里好几张票，一次支付覆盖好几张票。

A: 哦……那如果我换成"预订"当案例呢？

B: 那就反过来。同一个预订实例，会有多个和票相关、和支付相关的事件。而且，取消一场演唱会，可能一下子影响一大堆预订。

A: 我开始感觉到了……选"票"当案例，和选"预订"当案例，画出来的流程根本不是同一个流程。

B: 你正踩在今天最重要的那块石头上。我把它说透——案例，不是数据给你的，案例是一个建模的选择（choice）。这就是案例概念，English 是 case notion。

A: 等一下，我得把这句话嚼烂。你是说，数据库里就算有个字段叫"case ID"，那也不是真正的案例？真正的案例是我"选"出来的？

B: 这正是必须打破的最大误解。很多人以为"案例 = 数据库里那个叫 case ID 的字段"。错。那个字段只是某个人当初的一个选择。同一片数据，你选票、选预订、选客户当案例，会得到三个完全不同的流程、三套完全不同的洞察。

A: 这就像……地质勘探里，决定钻哪一层。同一片地，你钻浅层的砂岩、还是深层的灰岩，取出来的是完全不同的东西。层不是地"给"你的，是你"选"的。

B: 这个比喻今天我要你牢牢记住。案例概念 = 选择钻进哪一层。钻错层，后面再精密的算法都在分析错的东西。

A: 那有没有"好选"的情况和"难选"的情况？

B: 有。教材给了个相对简单的例子——招聘。有职位空缺（vacancy）和申请（application）。活动有：开放职位、申请、面试、录用、关闭。一个职位空缺对应多个申请。

A: 那这里案例选谁？

B: 你试试。

A: 一个空缺对应多个申请……如果我选"申请"当案例，每份申请走自己的：被提交、被面试、被录用或拒。这好像挺顺的？

B: 顺，因为这里是一对多（one-to-many），不是多对多。教材明确说，这种情况"还算简单"。空缺和申请之间是清清楚楚的一对多，你选申请当案例，基本不出乱子。

A: 那"难"的情况，是不是就是多对多？

B: 你已经预判到下一段了。教材紧接着抛出了亚马逊的例子。我们这集会用它贯穿到底。订单（order）、商品项（item）、包裹（package）、路线（route）。

A: 这几个之间什么关系？

B: 一个订单 1 到多个商品项——一对多。多个商品项可能打进同一个包裹，多个包裹又可能来自不同订单——这里就出现了多对多（many-to-many）。一个包裹走一条路线，多个包裹可能共用一条路线——多对一。

A: 所以亚马逊这片地里，订单、商品、包裹、路线交织成一张网，有一对多、多对一、还有最讨厌的多对多。

B: 对。教材画了一张具体的图：订单 1、订单 2、订单 3；商品 1 到 7；包裹 1 到 4；路线 1 到 3。它们之间的连线是一张网，不是几条平行线。

A: 那我问个要命的问题。在这种网里，案例到底选谁？

B: 这正是问题的核心——在多对多的网里，你选任何一个当案例，都会丢东西或者重东西。这就把我们逼到了今天的下半场。但在往下钻之前，我们先停一下，回到地面看看地图。

A: 对，中点了，我来对一下地图。我们现在走到哪了？

B: 你来说，我听。

A: 好。我们出发点是——事件日志不是被给的，是被造的，像地底的原油。第一站，认岩：事件日志的元模型，五层级、属性、事务生命周期、活动类型 vs 实例，被 XES 也就是 IEEE 1849-2023 固定。第二站，地震勘探：点图，一个事件一个点，三种纵轴、绝对相对两种时间，钻之前先看纹理。第三站，取油：大多数系统不存事件，得从几万张表里重建，三种铲子——事务日志、多列时间戳、变更表。第四站，也就是我们现在站的地方：选层——案例概念。案例不是数据给的，是你选的；选错层，全盘皆错；多对多的网里，怎么选都难。

B: 这张地图你画得完整，连因果链都接上了。而且你刚好停在了今天的分水岭上——前半场是案例中心（case-centric）的世界，我们假设一次只钻一层。后半场，我们要承认一个现实：地层本来就是相互重叠的。

A: 重叠的地层……这就是对象中心（object-centric）吧？

B: 正是。我们正式往下钻。先把前半场那个隐藏假设挑明——我们到现在为止，一直假设"案例是孤立看待的"（cases are considered in isolation）。

A: 孤立看待……意思是每个案例自顾自走一条线，互不相干？

B: 对。所有主流的建模记号——你画的那些流程图——都是在孤立地建模单个实例的生命周期。register request、examine、check ticket、decide、pay 或 reject，一条线走到底。少数例外，比如对象中心 Petri 网、Celonis 的 Process Sphere、Proclets 这些。

A: 但现实里案例真能孤立吗？亚马逊那张网摆在那……

B: 这正是要打破的假设。我给你制造下一个困惑。回到亚马逊。一个事件——"place order"，下单。这一个事件，到底属于哪一个案例？

A: 呃……它属于这张订单。

B: 可这张订单里有三个商品项呢。这个"下单"事件，难道不也和这三个商品项有关？

A: ……对啊。下单这一下，既是订单的事，也是这三个商品的事。它同时属于好几个对象。

B: 你正好撞上了对象中心的核心。前半场我们假设一个事件属于一个案例。现实是——一个事件，可以同时牵涉多个对象。教材为此换了一个事件的定义。

A: 怎么个新定义法？

B: 旧的：事件大概就是活动加时间戳，属于某个案例。新的，对象中心的：事件 = 活动 + 时间戳 + 对象集合 + 属性。English：event = activity + timestamp + objects + attributes。注意中间那个——objects，是复数，是一组对象。

A: 关键变化就是从"一个案例"变成"一组对象"。

B: 对。而且对象是带类型的（typed），一个事件可以引用任意数量的对象。教材举例：一个"place order"事件可以引用多个商品项；一个"pick item"事件只引用一个商品项；一个"failed delivery"事件，可能引用一个包裹、一个或多个商品项、一个或多个订单。

A: 所以同一个流程里，不同事件牵涉的对象数量都不一样。这就是对象中心事件日志吧？

B: 这是今天的大术语：对象中心事件日志，English 是 Object-Centric Event Log，缩写 OCEL。先记住这个定义，后面我们会讲它的标准。但现在有个现实问题——

A: 我猜：现有的工具，那四种发现算法，吃得下这种"一个事件多个对象"的日志吗？

B: 你问到点子上了。吃不下。教材直接问："怎么把这个加载进你最爱的流程挖掘工具？"答案是：你必须挑一个案例标识符（case identifier）。可这正是我们前面说的难题——在多对多的网里，挑哪个？

A: 所以为了用旧工具，我被迫要把这个"多对象"的事件，压回成"单案例"的形式？

B: 正是。这个压扁的动作，有个专门的名字，也是今天的核心术语：展平，English 是 flattening。

A: 展平。听着就有"把立体压成平面"的意思。

B: 这个直觉对极了。在我们的比喻里——地层本来是立体重叠的，展平就是只从一个钻孔的视角，把它当成一根单一的岩芯来读。你强行把三维的构造，投影成一维的一根柱子。

A: 那具体怎么展平？

B: 两步。第一，挑一个对象类型当案例概念。第二，对于每个事件，按这个类型的每一个对象，把事件复制一份。教材用了那个"send package"的例子，我带你走。

A: 来。

B: 有个事件，place order，2019 年 12 月 26 号，它的订单集合是 {991283}，商品项集合是 {885038, 885039}，包裹集合是空的。现在问：如果用订单当案例，这个事件出现几次？

A: 订单集合里只有一个订单，那……出现一次？

B: 对，一个事件。如果用商品项当案例呢？

A: 商品项集合有两个，885038 和 885039……那要复制成两份？两个事件？

B: 正是，两个事件。那如果用包裹当案例？

A: 包裹集合是空的……那这个事件，一次都不出现？它直接消失了？

B: 你亲手推出了展平的三种病理。这是今天必须记住的三个术语——收敛、发散、缺陷，English：convergence、divergence、deficiency。我们一个一个钻。

A: 先说刚才那个"消失"的吧，最直观。

B: 那是缺陷（deficiency）。定义：原始日志里那些事件，在展平后的日志里找不到对应的事件，就会无意中从数据集里消失。你选了包裹当案例，那所有不牵涉包裹的事件——下单、拣货——全都蒸发了。

A: 这就像……我决定只钻深层的含油层，结果浅层那个油袋，我的钻头压根没穿过，我就当它不存在了。

B: 这个比喻精确。发散和收敛我先讲收敛，因为它和缺陷正好相反。

A: 收敛是"复制成两份"那种？

B: 对。收敛（convergence）：一个事件如果牵涉到所选类型的多个对象，它就会被复制，可能导致无意的重复。回到那个例子，用订单当案例时一切正常；可一旦某个"send package"事件牵涉两个订单 99001 和 99002，它就被复制成两行，一行挂 99001，一行挂 99002。

A: 同一个真实事件，在日志里变成了两条。那……如果我之后去算成本、算次数，岂不是把它算重了？

B: 你立刻看到了恶果。教材在收敛那一页就直接问：当事件被复制了，你怎么算成本、时间、频率？一次真实发货，被数成了两次。

A: 这就像我从两个不同的角度去钻同一个油袋，结果在账本上把它记成了两个油袋。明明只有一桶油，我以为有两桶。

B: 收敛的比喻就是这个——从不同角度重复计数同一个油袋。那最后一个，发散，最微妙，你得集中精神。

A: 发散（divergence），来。

B: 定义：事件如果牵涉到的是"没被选作案例概念的那个类型"的不同对象，这些事件会被错误地认为彼此存在因果关系。我用例子带你，你跟紧。

A: 我盯着。

B: 假设用订单当案例。一个订单 99001，里面有三个商品项 88001、88002、88003。现在发生了一串事件：pick item 88001、pick item 88002、pack item 88002、pack item 88001、pick item 88003、pack item 88003。注意，这些事件的订单都是 99001，但商品项各不相同。

A: 嗯，全是订单 99001 名下的，但拣的、打包的是不同的商品。

B: 现在，因为你选了订单当案例，商品项的身份被"压"掉了。在工具眼里，这条订单的轨迹就成了：pick、pick、pack、pack、pick、pack——一长串看不出谁是谁的事件。

A: 等一下……工具会以为这是一个顺序流程？先 pick 再 pick 再 pack？可实际上，每个商品是各自独立地先 pick 后 pack 的！

B: 你抓住了发散的本质。真实情况是：对每一个商品，pick 在 pack 之前，这是固定顺序。但因为商品身份被压掉，工具把不同商品的事件混在一条线上，于是要么以为它们有奇怪的因果关系，要么以为它们是并发的——而真实的"每个商品 pick 在前 pack 在后"这个铁律，反而看不见了。

A: 所以发散是……我的钻头本该穿过三个独立的小油袋，结果因为我只认订单这一层，把三个袋子的信号搅成了一锅，分不清哪股油来自哪个袋子，连"先后"都乱了。

B: 这个比喻立住了。教材在发散那两页强调了两件事：一是"事情本来有固定顺序，但这个顺序看不见了"；二是由此产生的并发与因果的错乱。

A: 我把三种病理一起复述，免得混。缺陷：选了某类型当案例，不牵涉该类型的事件直接消失——我的钻头没穿过的油袋当它不存在。收敛：一个事件牵涉所选类型的多个对象，被复制成多份——从多个角度把一个油袋数成几个，成本频率全算重。发散：被压掉身份的那些其它对象的事件，被错当成有因果或并发——三个小油袋的信号搅成一锅，先后乱了。

B: 三个都说准了，而且比喻自洽。现在你可能会想——这是不是亚马逊这种变态例子才有的毛病？

A: 我正想问。这是不是个别情况？

B: 这正是教材要纠正的最后一个误解。它说，"相关性？看看任何一个数据模型就知道了！"不管你用 Chen 记号、鸦爪记号还是 UML 类图，订单和商品是一对多，订单和包裹是多对多，订单和支付勉强一对一。然后它点了一句要命的话：很少有关系是一对一的。

A: 哦……只要数据模型里有一个多对多，甚至一对多，对象中心的问题就冒出来了。而真实世界几乎全是多对多和一对多。

B: 所以结论是——一个单一的案例概念，根本不够用。教材原话：a single case notion is not enough。对象中心不是特例，案例中心才是那个简化。

A: 这我得调整一下世界观。我一直以为案例中心是常态、对象中心是高级变体。其实反了——重叠的地层才是真实地质，单一岩芯只是我们为了好分析做的简化。

B: 你这个认知翻转，正是这一段的目的。那么问题来了：既然展平这么多病，我们该怎么办？

A: 是啊。难道每次都得忍受收敛发散缺陷？还是说有别的路？

B: 有别的路。这就是下一段——OCEL 标准和对象中心流程挖掘。比喻往前推一步：与其每次钻一个孔就重新理解一遍地层，不如先建一份完整的三维地质模型，需要哪个视角再从模型里取。

A: 一次建模，多次取用。这思路我喜欢。那 OCEL 标准长什么样？

B: OCEL 现在到了 2.0 版，标准在 www.ocel-standard.org。我不带你抠它的图，给你抓骨架。它的核心是把两样东西都显式化：事件这边，有事件类型（也就是活动）、时间戳、事件属性；对象这边，有对象、对象类型、对象属性。

A: 和案例中心比，多出来的就是"对象"这一整套？

B: 对，而且最关键的是中间的连接——事件和对象之间有"has objects"的关系，还带限定词（qualifier），说明这个对象在这个事件里扮演什么角色。对象和对象之间也能有关系。它把"一个事件牵涉哪些对象、各是什么角色"原原本本地记下来，不压扁。

A: 所以 OCEL 就是那份完整的三维地质模型——它把重叠的地层照实存下来，不强行投影成一根岩芯。

B: 这个比喻贯穿得好。那存下来之后怎么用？这就是今天的另一个大术语：对象中心流程挖掘，English 是 Object-Centric Process Mining，缩写 OCPM。

A: OCPM 是另起炉灶发明全新算法吗？还是说能复用我们学过的那四种？

B: 这是最聪明的地方——它复用现有的案例中心技术，不重造轮子。教材给的方法三步：展平（flatten）、计算（compute）、折叠回去（fold back）。

A: 等一下，它居然还是要展平？我们刚骂完展平。

B: 问得好。区别在于——以前是只展平一次、只钻一个孔，然后就拿着那根残缺的岩芯当全部真相。OCPM 是从那份完整的三维模型出发，按每一个对象类型各展平一次，分别学出模型，最后再折叠回一个整体。

A: 哦！所以订单展一份、商品展一份、包裹展一份，各学各的流程，再拼起来。每一份都是局部正确的，拼起来还原全貌。

B: 正是。教材给了那个亚马逊的大例子：一份对象中心日志，22080 个事件、11300 个对象——200 个订单、8003 个商品项、1297 个包裹。对订单展平学一个模型，对商品项展平学一个，对包裹展平学一个。

A: 那"折叠回去"怎么保证拼对？

B: 教材点了两个关键要素。第一，活动标签要唯一——三个模型里的同一个活动得能对上。第二，对象在频率上要达成一致，靠的是"变量弧"（variable arcs）。比如同一个 send package 活动，在订单模型里算一次，在商品项模型里牵涉好几个商品——这些频率得能调和。教材里那些 2000 ≠ 8003、8003 ≠ 1297 的不等式，说的就是不同对象类型在同一活动上的数量对不齐，得靠变量弧来表达。

A: 所以最后折叠出来的，是一个对象中心的模型——比如对象中心 Petri 网，能同时显示订单、商品、包裹三条线怎么交织。

B: 对。Celonis 里就有对象中心的 DFG 和对象中心 BPMN，能展示三个对象类型、十几个活动怎么互动。开源这边也有一票工具，都挂在 ocel-standard 网站上。

A: 那退一步，OCPM 比"每次重新展平"到底好在哪？给我三条我能记住的。

B: 教材正好给了三条。第一，避免反复回源系统——你只抽取一次，得到一份系统无关的"单一真相来源"（single source of truth），之后要什么视角从这份里取，不用每次回 SAP 里捞。第二，能看清不同对象类型之间的交互——而问题往往就活在流程与组织实体的交界处。第三，避免单案例假设带来的扭曲——也就是从根上绕开收敛和发散。

A: 我把这三条对回比喻。一，建一次三维地质模型，省得每次重新勘探。二，能看清地层之间怎么搭接——油往往就藏在地层交界处。三，不再被单一岩芯的偏见误导，不重复计数也不搅混信号。

B: 三条都对上了，比喻也守住了。教材还顺手提了一句——OCPM 是"额外抽取，按需进行"。你保留传统的 XES 流程不动，需要对象中心视角时，再从源头按需抽成 OCEL 2.0，用专门的技术处理。两条路并行，不冲突。

A: 想深入的话教材推荐去上高级流程挖掘那门课。我们这集到这够用了。

B: 够用了。现在我们钻完了选层、看清了重叠地层、也学会了怎么建完整模型。但还剩最后一关——也是最容易被忽略，却最致命的一关。

A: 我猜是……数据质量？就算前面全做对了，要是取上来的油本身是脏的呢？

B: 你又预判到了。这是最后一段。在选择和映射的问题之外，还有数据质量问题（data quality issues）。比喻：你勘探对了、钻对了层、建对了模型，可如果你的岩芯样本本身被污染了，化验结果照样是错的。

A: 那数据质量能脏成什么样？

B: 教材分了四大类。第一，缺失数据（missing data）——该记的事没记。第二，错误数据（incorrect data）——记了，但记错了。第三，不精确数据（imprecise data）——记了，但颗粒度不够。第四，无关数据（irrelevant data）——相关的东西淹没在杂乱的结构里。

A: 我感觉这四类，可以套在我们前面那个元模型的每一层上？

B: 你这个直觉非常对，教材正是这么做的——它做了一张大网格，横着是元模型的各个部位：案例、事件、案例与事件的归属、属性、位置顺序、活动名、时间戳、资源……竖着是那四类问题。每个格子都是一种具体的毛病。我不念整张网格，给你挑几个最能咬到人的。

A: 好，挑狠的讲。

B: 缺失这一类里最阴的：一个案例真的执行了，但日志里根本没记——你分析的时候压根不知道它存在。还有"关联丢失"——事件和案例的归属关系没了，这叫相关性问题（correlation problem），你有一堆事件，却不知道哪个属于哪个案例。

A: 那不就抓瞎了。错误那一类呢？

B: 错误里典型的：日志里某些案例其实属于另一个流程，混进来了；或者某些根本没执行的事件被记了进来；或者时间戳记错了、资源指错了人。

A: 不精确那一类，我猜和时间戳有关？

B: 你猜得准。最经典的就是时间戳的粒度——只记到"天"，不记到"分钟"或"秒"。教材专门点了这个后果：粒度太粗，事件的精确先后就推不出来，并发的事件可能被硬排成全序（totally ordered）。还有资源只记到角色或部门，活动名太笼统，地址只到城市不到门牌。

A: 哦，时间戳只到天那个我特别有感觉——这不就直接威胁到我们最开头说的，时间戳是排序的命根子吗？粒度一粗，整个先后就糊了。

B: 你把这一关和第一关接上了，这正是它致命的原因。无关数据那一类我一句带过：无关的案例混进来又删不掉、无关的事件难以剔除，把真正重要的信号淹了。

A: 那既然知道会脏成这样，有没有"打井规范"，从源头让大家把日志记好？

B: 有。教材给了一套，叫日志记录指南，English 是 Guidelines for Logging，缩写 G4L。它一共有十一二条，我绝不会一条一条念给你——那是催眠。我按主题给你归成几束，你抓住背后的原则。

A: 好，归束讲，我要的是原则不是清单。

B: 第一束，关于"命名与结构"。引用名和属性名要语义清晰，而且要有一套受管理的、结构化的命名集合。一句话：别让字段名靠猜。

A: 名字要清楚、要统一管。第二束？

B: 第二束，关于"稳定与精确"。引用要稳定——标识符不要重用，不要依赖上下文，比如不要随时间、地区、语言而变。教材举了个真实的坑：有些系统按语言设置生成不同的日志，平白给分析添乱。还有，属性值要尽量精确；如果达不到该有的精度，要显式标出来——比如某些事件只知道日期不知道具体时刻，那就明确写"这只精确到天"。

A: 稳定的 ID、精确的值，做不到精确就老实承认。这其实就是在防我们刚说的"不精确数据"那一类。

B: 正是，G4L 和那四类质量问题是一一对着治的。第三束，关于"完整与忠实"。至少要部分排序事件、尽量记录事务信息、定期做自动一致性和正确性检查。还有两条特别重要：不要在用于分析的日志里聚合事件，也不要删除事件、要保证可追溯（provenance）。

A: 等一下，"不要聚合、不要删除"——这不就是在防我们前面学的展平和质量问题吗？你一聚合，颗粒度就粗了；你一删除，事件就缺失了。

B: 你把指南和病理对上了，这正是它的用意。第四束，关于"可比与隐私"。要保证日志在时间上、在不同案例组或流程变体之间是可比的——记录原则别偷偷变，要变就报备，否则没法做比较式挖掘。最后，要在不丢失有意义关联的前提下保护隐私。

A: 我把四束原则收一下：命名要清晰统一；引用要稳定、值要精确、不精确就标明；要完整忠实——别聚合、别删除、留追溯；要可比、要护隐私。这就是打井的最佳实践。

B: 而这一整套，最后浓缩成今天最后一个、也是分量最重的术语：GIGO，Garbage In, Garbage Out。垃圾进，垃圾出。

A: 这个我熟。但放在今天这个语境里，它的分量好像不一样了。

B: 因为今天整集就是在给这四个字做注脚。教材最后画了一个极简的图：record，记录；analyze，分析。中间一根箭头。意思是——你分析的质量，永远不会超过你记录的质量。算法再强，喂进去垃圾，吐出来还是垃圾。

A: 在我们的比喻里，GIGO 就是——如果你的地质图本身就是错的，那你勘探再仔细、钻探再精密，也是在错的地方打井。地图错了，全盘皆错。

B: 这是今天比喻的终点，也是整集的主题句。事件数据这门功夫，难就难在它在算法之前、在所有光鲜的模型之前。教材的结论原话很实在：抽取往往复杂、痛苦，而且消耗掉你大部分的时间。

A: 那我来做今天的总收。如果只能带走一句话——算法再强，垃圾进垃圾出。事件数据像原油，勘探、提取、净化，三步缺一不可。

B: 这句话立住了整集。我再帮你把六站串成一条线，你听听是不是闭环了。

A: 来，串。

B: 第一，认岩——事件日志的元模型，五层级加属性加事务生命周期，被 XES 也就是 IEEE 1849-2023 固定，注意分清活动类型和实例。第二，地震勘探——点图，钻之前先看纹理，三种纵轴、绝对相对两种时间。第三，取油——大多数系统不存事件，得从几万张表里用三种铲子重建。第四，选层——案例概念，案例是选择不是给定，这是今天的心脏。第五，重叠地层——对象中心是常态，展平会带来缺陷、收敛、发散三种病。第六，建模与净化——OCEL 标准存下完整三维模型，OCPM 复用旧算法再折叠，G4L 是打井规范，GIGO 是终极警告。

A: 闭环了。我发现今天最颠覆我的，是那个认知翻转——案例中心不是常态，对象中心才是真实地质。我一直把简化当成了真相。

B: 这正是今天最该带走的东西。而且你注意到没有——我们这一路其实在给前十集补一块地基。前面四种发现算法，都假设有一份干净的、案例中心的日志。今天我们才知道，那份日志本身是被造出来的，每一个造的动作都有代价。

A: 那下一集呢？我们手里现在既有模型，又有事件日志了。

B: 这就接到下一站。我们之前说过"从建模型到检验模型"。但在检验之前，得先想清楚——拿什么去检验？答案就是今天这份来之不易的事件日志。EP12，我们进入一致性检查（Conformance Checking）第一部分：有了模型，也有了真实跑出来的日志，怎么判断模型和现实到底对不对得上、差在哪。

A: 从"现实长什么样"到"模型和现实合不合"。地质图建好了，下一步是拿它去对真实的地层。我已经等不及了。

B: 那我们 EP12 见。今天记住一件事就够——在你迷信任何模型之前，先问一句：喂进去的，是原油，还是垃圾？
