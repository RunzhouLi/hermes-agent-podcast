**安安：** 我先抛一个让我半夜想不通的场景啊。我在网上买了个东西，订单已经走到一半了——钱付了，仓库也开始备货了——结果我突然反悔，点了"取消订单"。你说，这个时候系统到底该干嘛？

**林老师：** 这正是今天的核心问题。前几集我们画的流程，大多是"一切顺利"的主干道：开始、做几件事、结束。可现实里，**订单处理已经完成了一半，突然失败、突然取消、或者需要把已经做完的事撤销回来——BPMN 到底怎么把这些表达出来？**

**安安：** 对！我直觉是"那就加个判断框呗"。但付都付了、货都备了，一个菱形判断框好像不太够。

**林老师：** 不够。这一集我们要补的，正是 BPMN 里专门处理"出意外、要中止、要善后"的一整套高级词汇。学完之后，你看任何一个真实流程，"万一……怎么办"这一类问题，你都能用对应的记号画出来。

**安安：** 那今天这集，我替听众当那个一路追问的人。

**林老师：** 好。我们正式开始。

## 1. 路线图（Roadmap）

**林老师：** 先给你今天的地图，六个站，外加一段练习。

1. **终止结束事件** Terminate End Event —— 怎么"把整个流程一下子全停掉"。
2. **事件子流程** Event Sub-Process —— 流程跑着跑着，怎么塞进一段"随时可能被触发"的处理。
3. **文本注释** Text Annotation —— 怎么给图加说明，但又**不改变**流程的执行。
4. **边界事件** Boundary Event —— 怎么在"某个具体活动正在做的时候"插一个反应。
5. **错误事件** Error Event —— 某一步真的失败了，怎么往上抛、怎么接住。
6. **补偿** Compensation —— 已经做完的事要"撤销/善后"，怎么画。
7. 最后用 **第 5 周的练习**和两份**参考答案（5.2、5.3）**当检查点，验收一下。

**安安：** 我先记一个记忆钩子：你之前说过，可以把流程想成**一场已经开演的舞台剧**？

**林老师：** 对，这个比喻今天会一直用。一场戏开演之后：什么时候**直接叫停整场**（终止）、什么时候**临时插一段应急桥段**（事件子流程）、某一幕边上贴个**随时打断的提示**（边界事件）、演出中**真的出岔子**（错误）、以及谢幕后**返场把演过的部分倒回去补救**（补偿）。六个站，对应六种"戏演到一半的意外"。

## 2. 前置回顾（Prerequisite，一分钟把旧词捡回来）

**林老师：** 在上新内容之前，我用一分钟把前几集（EP02 到 EP04）你需要的旧词捡回来，因为今天全建在它们上面。

- **令牌** Token：你可以想成流程里一颗会跑动的"小棋子"，它走到哪，哪个活动就在执行。流程"在做什么"，本质就是"令牌现在在哪儿"。
- **事件** Event：画成圆圈。**开始事件**（细圈）、**中间事件**（双圈）、**结束事件**（粗圈）。
- **网关** Gateway：菱形。今天会用到两种——`×` 是**排他网关**（XOR，走其中一条路），`+` 是**并行网关**（AND，几条路同时走）。
- **子流程** Sub-Process：把一坨活动打包成一个可以折叠的方块，这是 EP04 的内容。
- **中断 / 非中断** Interrupting / Non-interrupting：这一对今天会反复出现。**中断**＝触发之后，把原来的活儿叫停；**非中断**＝触发之后，原来的活儿照常进行，只是另起一条支线。

**安安：** 这对"中断 / 非中断"我先立个 flag，感觉今天会被它绊好几次。

**林老师：** 你很有预感。它会在"事件子流程"和"边界事件"两个地方各出现一次，**长得像、含义不同**，是今天最容易混的点之一。我们到时候专门停下来对比。

## 3. 核心框架（Core concept：高级事件 = 一套"意外与善后"的结构化词汇）

**林老师：** 在拆六个记号之前，先给你一句话的总纲，这句话能帮你把六个站串成一个整体——

> **BPMN 的高级事件，不是"额外的花样"，而是一套专门描述"意外、中止与恢复"的结构化词汇。**

**安安：** 能不能再翻译得更白一点？

**林老师：** 可以。普通流程回答的是"事情顺利时，按什么顺序做"。高级事件回答的是另外四个问题：

1. "**要不要现在就全停？**" → 终止结束事件。
2. "**这件随时可能冒出来的事，谁来接？**" → 事件子流程 / 边界事件。
3. "**这一步真的失败了，怎么办？**" → 错误事件。
4. "**已经做完的事，现在要反悔，怎么收拾？**" → 补偿。

**安安：** 所以六个记号其实是在回答不同的"万一"。

**林老师：** 正是。记住这个"问题—记号"的对应关系，今天就不会迷路。最后回顾的时候，我们会把这张对应表完整地再过一遍。好，进第一站。

## 4. 第一站：终止结束事件 Terminate End Event

**林老师：** 先从一个最干脆的开始。前面说过，普通的**结束事件**只完成"走到它这条路"。但有时候——用课件的原话——**"光有一个结束事件还不够"（Sometimes, an end event is not enough）**。

**安安：** 为什么不够？结束就结束了呗。

**林老师：** 因为普通结束事件**只熄灭走到它那一颗令牌**。如果流程里还有别的令牌在跑（比如并行的另一条支线还在忙），那条支线**不会**因为你这边结束就停下。它会继续跑，整个流程实例要等所有令牌都跑完才算真正结束。

**安安：** 哦——所以如果我想"立刻、马上、把整盘棋全部掀掉"，普通结束事件做不到。

**林老师：** 对。这就要请出今天第一个术语。

> **【术语卡 · 双语协议】**
> - **中文：** 终止结束事件
> - **英文：** Terminate End Event
> - **记号：** 一个**粗圈的结束事件**，圈里是一个**实心的黑圆点**（实心圆是它的专属标记）。
> - **大白话：** "全场停"按钮。一旦有令牌走到它，它会把**当前这个流程范围里所有的令牌**——包括所有还在跑的并行支线、所有嵌套的子流程里的令牌——**统统清空**，流程范围立刻结束。
> - **例子：** 房贷审批。后面马上讲。

**林老师：** 课件给了它四条性质，我逐条翻译：

1. **Removes all tokens from the parent process and all its subprocesses** —— 清除它所在流程、以及该流程下面所有子流程里的全部令牌。一锅端。
2. **Parent process continues as usual** —— 注意这条很关键，也最容易误解：如果这个终止事件是**装在一个子流程里**的，那它清空的是**这个子流程内部**；对于**外面那层更大的父流程**来说，它只是看到"这个子流程结束了"，然后**照常往下走**。换句话说，终止**不会**顺着往上爬、把外层也一起干掉。
3. **Signals a negative outcome to the environment** —— 它通常代表一个"负面结局"，对外表示"这事儿黄了 / 被否决了"。
4. **Use sparingly** —— **省着点用**。因为它很"暴力"，滥用会让模型很难读懂。

**安安：** 等一下，第 2 条我要确认。终止到底停的是"哪一层"？

**林老师：** 好问题，我用舞台剧讲。把每个子流程想成"戏中戏"。终止事件出现在哪一层戏里，就把**那一层戏以及它里面的所有戏中戏**全部叫停、落幕。但**外面那台大戏**不受影响，它只当这出"戏中戏"演完了，继续往下演。所以终止的"全停"，范围是**它自己这一层往下**，不是"整个剧院"。

**安安：** 那如果终止事件就在最外层、最顶层呢？

**林老师：** 那它上面没有"更大的戏"了，于是效果就是**整个流程实例立刻结束**。这也是大家最直觉的那种"全停"。

**林老师：** 来看课件的例子——房贷审批。

> **【图示 · 用令牌讲】房贷审批**
> 流程开始后遇到一个**并行网关 `+`**，令牌一分为二，两条支线**同时**进行：
> - 支线一：**Check debt（查负债）**，做完接一个**排他网关 `×`**：如果是 **high debt（高负债）**，走向一个**终止结束事件**；如果是 **low debt（低负债）**，正常往下。
> - 支线二：**Check house value（查房产价值）**。
> 两条支线本应在后面用**并行汇聚 `+`** 合流，然后 **Provide mortgage（放贷）**。

**林老师：** 现在请你跟着令牌想：假设"查负债"先出结果，是 **high debt**。这时候我已经知道——这笔房贷肯定批不了了。

**安安：** 但是另一条支线"查房产价值"可能还在吭哧吭哧地查……

**林老师：** 没错。如果我用一个**普通结束事件**结束高负债这条路，"查房产价值"那颗令牌**还在跑**，流程实例不算结束，白白浪费。而且后面那个并行汇聚 `+` 在傻等一颗永远不会来的令牌，逻辑还卡死了。

**安安：** 所以这里就该上"全场停"——终止结束事件，把还在查房产的那条支线一起清掉，直接给出"否决"的结局。

**林老师：** 完全正确。**这就是终止事件最经典的用法：在并行的多条支线里，只要有一条断定"整件事可以停了"，就用终止把所有还在跑的令牌一次清空**，而不用费劲去画一堆取消另一条支线的网关。

**安安：** 我用一句话给它收尾：普通结束 = "我这条路走完了"；终止结束 = "这一层全体令牌，立刻解散"。而且要省着用。

**林老师：** 漂亮。这就是**第一个易混点的答案**：终止结束事件 vs 普通结束事件。记住"清一颗" vs "清一层"。

**【转场】** 终止是"全停"。但现实里更多时候不是停，而是"流程跑着跑着，突然冒出来一件事得有人接"。这就引出第二站。

## 5. 第二站：事件子流程 Event Sub-Process

**林老师：** 先复习一秒：普通子流程，是怎么"启动"的？

**安安：** 有一颗令牌从外面顺着箭头流进去，它就开始跑。

**林老师：** 对，**A sub-process starts with a token——普通子流程靠"令牌流入"启动**。现在记住这句对照——

> **A sub-process starts with a token. An event sub-process starts with a trigger.**
> 普通子流程靠**令牌**启动；事件子流程靠**触发器（一个事件）**启动。

> **【术语卡 · 双语协议】**
> - **中文：** 事件子流程
> - **英文：** Event Sub-Process
> - **记号：** 画在某个流程或子流程**内部**的一个**虚线边框**的方块；它的**开始事件**画在左上角。
> - **大白话：** 一段"预先埋好、平时不动、某个信号一响才启动"的应急处理。它**不接在主干道上**——没有箭头流进去，也没有箭头流出来。
> - **例子：** 订单处理过程中"客户改地址"或"商品缺货"的处理。后面讲。

**林老师：** 它的语法语义，课件给了四条，我翻译：

1. **In a process or sub-process** —— 它住在某个（子）流程**里面**。
2. **Not part of normal token flow** —— 它**不在**正常的令牌流里。主干道的令牌平时根本不经过它。
3. **No sequence flows in/out** —— 它**没有**进出的顺序流箭头。它怎么启动？靠左上角那个开始事件被**触发**。
4. 然后是关键的一对——它的开始事件分**中断**和**非中断**两种。

**安安：** 来了，"中断 / 非中断"。这次它怎么表现？

**林老师：** 看开始事件的圈是**实线**还是**虚线**：

- **中断式（Interrupting）**：开始事件画**实线圈**。一旦触发，它会**清空父流程里所有的令牌**（也就是把主干道正在做的事叫停），然后跑这段事件子流程，跑完之后父流程按这段处理的结果继续。课件原话：**Interrupting: removes all tokens from parent process and continues normally**。
- **非中断式（Non-interrupting）**：开始事件画**虚线圈**。触发之后，**对父流程毫无影响**——主干道照常跑，事件子流程**另起一条支线并行**地处理。课件原话：**Non-interrupting: no influence on parent process**。

**安安：** 我抓一下重点：同样一个"信号响了"，中断式是"先把手头的活停了，去处理这件事"；非中断式是"手头活不停，旁边再开一个窗口同时处理"。

**林老师：** 一字不差。来看课件那个订单的例子，我们用令牌走一遍。

> **【图示 · 用令牌讲】带事件子流程的订单处理**
> **主干道：** `PO received（收到订单）` 开始 → **Register PO（登记订单）** → **Check availability（查可用性）** → **Handle PO（处理订单）** → `PO fulfilled（订单完成）` 结束。
> 在这个流程内部，埋了两段**事件子流程**：
> - **非中断式**，触发器是 **address change received（收到改地址请求）**：里面是 **Change address（修改地址）**，做完 `address changed`。
> - **中断式**，触发器是 **items not available（商品缺货）**：里面是 **Send PO response（发缺货通知）**，`notification sent`，然后订单到此中止。

**林老师：** 跟我走令牌。第一种情况：订单正在 **Check availability** 这一步，客户突然说"我要改收货地址"。

**安安：** 改地址这件事……不该把整个订单停掉吧？我地址改完，订单还得继续处理啊。

**林老师：** 对！所以"改地址"用**非中断式**事件子流程。触发的瞬间，主干道那颗令牌**继续**往下跑（该查可用性查可用性），**同时**旁边另起一颗令牌跑 **Change address**。两边互不打扰。

**安安：** 那"缺货"呢？

**林老师：** "缺货"是个坏消息，意味着这单**没法正常完成**了。所以它用**中断式**。一旦触发，父流程里所有令牌被**清空**——主干道停了——转而去跑 **Send PO response**，给客户发个缺货通知，然后这单就此中止。

**安安：** 我突然意识到一个问题：这个"中断式事件子流程"听起来……和"终止"是不是有点像？都清空令牌。

**林老师：** 非常好的警觉！区别在于：**终止**是"清空之后就结束，给个负面结局，啥也不干了"；**中断式事件子流程**是"清空主干道之后，**还要去跑一段处理**"（比如发通知、做善后）。一个是"停了拉倒"，一个是"停了之后接管"。

**安安：** 懂了。终止是保安直接清场关门；中断式事件子流程是保安清场之后还有个专人来善后。

**林老师：** 这个类比很到位。

**【小结这一站】** 事件子流程 = 埋在流程内部、靠信号触发、没有进出箭头的一段处理；实线圈=中断（停主干道再处理），虚线圈=非中断（主干道照跑，旁边并行处理）。

**【转场】** 在我们冲向下一个执行类记号之前，先插一个**完全不影响执行**的小东西，把它讲清楚，免得后面混进来。那就是文本注释。

## 6. 第三站：文本注释 Text Annotation

**林老师：** 这一站特别短，但概念上很重要，因为它是今天**唯一一个不参与执行**的记号。

> **【术语卡 · 双语协议】**
> - **中文：** 文本注释
> - **英文：** Text Annotation
> - **记号：** 一个**只有一边带方括号"["** 的开口小框，里面写文字；用一条**虚线（关联 association）**连到任意元素上。
> - **大白话：** 就是给图**贴便利贴 / 写批注**。给读图的人看的说明，仅此而已。
> - **例子：** 在某个活动旁边贴一句"此处需法务复核"。

**林老师：** 课件就一句核心话：**Text annotations are comments and do not affect the token flow——文本注释是注解，不影响令牌流。** 你可以用关联线把它**挂到任何东西上**（Attach them to anything using an association）。

**安安：** 所以这里有个对比题对吧？文本注释 vs 真正会执行的控制流元素。

**林老师：** 正是今天**第三个易混点**。判断标准就一条：**令牌会不会经过它？**

- 文本注释：令牌**永远不经过**它。它连的是**虚线关联**，不是实线箭头。它存在或不存在，流程**怎么跑一模一样**。它只改变"人读起来好不好懂"。
- 控制流元素（活动、网关、事件、顺序流）：令牌**会经过**，它**真的改变**流程怎么跑。

**安安：** 一个超简单的记法：**虚线关联 = 给人看的；实线箭头 = 给令牌走的。**

**林老师：** 完美。注意它和"事件子流程"虽然都可能画虚线，但虚线的**对象**不同——事件子流程是虚线**边框**＋虚线**圈**表示触发方式，文本注释是虚线**关联线**表示"只是挂个说明"。别看到虚线就划等号。

**【转场】** 好，把"不执行"的讲完了。接下来三站全是硬核执行：边界事件、错误事件、补偿。它们仨经常一起出现，是今天的重头戏。先讲边界事件。

---

## 7. 第四站：边界事件 Boundary Event

**林老师：** 先建立一个对比。我们以前见过**中间捕获事件**（catching intermediate event），它**站在主干道上**，令牌走到它，**停下来等**某个触发——课件说 **Catching intermediate events: respond to triggers at certain points（在特定的点上响应触发）**。

**安安：** 关键词是"点"——令牌必须正好走到那个点上。

**林老师：** 对。但现实里很多意外，不是"在某个点"，而是"**在某件事正在做的整个期间**，随时可能发生"。这就要请出边界事件——课件：**Boundary events: respond to triggers during activities（在活动进行期间响应触发）**。

> **【术语卡 · 双语协议】**
> - **中文：** 边界事件
> - **英文：** Boundary Event
> - **记号：** 一个事件圆圈，**贴在某个活动（或子流程）的边框上**，它的"肚子"里画着触发类型的小图标（消息、定时器、错误、信号、补偿……）。
> - **大白话：** 给某个活动**边上贴一个"随时待命"的感应器**。只要这个活动还在执行，这个感应器就一直盯着；对应的触发一来，它就发难。
> - **例子：** 给"备货发货"这个活动边上贴一个"收到取消消息"的边界事件。

**林老师：** 它也分中断和非中断，这是今天**第四个易混点**，我们重点讲。

- **中断式边界事件（Interrupting）**：圈画**实线**。触发的瞬间，把这个活动**正在做的令牌拿掉**——也就是**打断、取消这个活动**——然后令牌从边界事件**引出的那条新路**继续走。
- **非中断式边界事件（Non-interrupting）**：圈画**虚线**。触发之后，活动**照常继续做**，同时从边界事件**另引一条支线**并行处理。课件原话：**Similar semantics: do not remove tokens from attached process（语义类似，但不从所贴的活动上拿走令牌）**。

**安安：** 又是那对"中断 / 非中断"！我现在大概抓到规律了：**实线 = 打断**、**虚线 = 不打断、另开支线**。无论是事件子流程还是边界事件，这条规律都成立？

**林老师：** 完全成立，这就是为什么我让你早早立 flag。**实线圈打断、虚线圈不打断**，这条规律今天通吃。

**安安：** 那"事件子流程"和"边界事件"到底差在哪？它俩都靠触发、都分中断非中断……

**林老师：** 这是今天**第二个、也是最容易混的易混点**，我专门停下来对比。看**贴在哪、管多大范围**：

- **边界事件**：**贴在某一个具体活动的边框上**，它**只在那个活动执行期间**有效。活动一结束，这个感应器就撤了。它管的是"**这一个活动**"。
- **事件子流程**：**画在整个（子）流程内部**，在**整个流程运行期间**都待命。它管的是"**这整段流程**"。

**安安：** 哦——一个是"贴在某一幕边上的提示"，一个是"整场戏期间都待命的应急预案"。范围不一样。

**林老师：** 就是这个画面。再补一句实操经验：如果你要响应的事"只跟某一个活动有关"，用边界事件贴上去最清楚；如果"在流程任何时候都可能发生"，用事件子流程更合适。

**林老师：** 看课件的例子，用令牌走一遍。

> **【图示 · 用令牌讲】带取消的报价—发货流程**
> 主干道：**Prepare quote（准备报价）** →（`order received` 客户下单）→ **Ship goods（发货）** → **Archive order（归档订单）**。
> 在某个活动（比如"准备报价/等待下单"这一段）的边框上，贴一个**消息边界事件 cancel PO（收到取消采购单的消息）**，从它引出 → **Handle cancellation（处理取消）**。
> 旁边有一个 **Customer（客户）** 泳池，取消消息就是客户发来的。

**林老师：** 跟我走：流程正在等客户下单 / 正在准备阶段，这时候客户那边发来一条"我要取消"的消息。

**安安：** 这个取消……应该是要打断的吧？都取消了，还准备啥。

**林老师：** 对，所以这里用**中断式**消息边界事件。令牌被从当前活动上**拿走**，转去走 **Handle cancellation（处理取消）**，然后归档。原本的"发货"自然就不会发生了。

**安安：** 那你提到的**定时器边界事件**呢？

**林老师：** **Timer boundary event（定时器边界事件）**，记号是活动边上贴一个"小钟表"。典型用法：给某个活动设个时限，比如"等客户确认，最多等 24 小时"。中断式的话，超时就打断它，走"超时处理"那条路。这就是"在活动进行期间盯着时间"的感应器。

**安安：** 我发现边界事件的触发类型可以有好几种？

**林老师：** 对，课件最后一页 **But there's more（还不止这些）** 列了一排：**compensation（补偿）、message（消息）、timer（定时器）、error（错误）、signal（信号）** 等等，都能做成边界事件贴在活动上。今天我们重点用到其中两个——**error（错误）** 和 **compensation（补偿）**，它们正好是接下来两站。

**【小结这一站】** 边界事件 = 贴在某个活动边框上的"随时待命感应器"；实线打断该活动、虚线不打断另开支线；触发类型有消息、定时器、错误、信号、补偿等。

**【转场】** 我们刚说边界事件可以是"错误"类型。那"错误"到底怎么抛、怎么接？进第五站。

## 8. 第五站：错误事件 Error Event

**林老师：** 一句话引入，还是课件原话：**Sometimes, things go wrong and we need to recover——有时候事情真出岔子了，我们得能恢复。**

**安安：** "出岔子"——这跟前面的"取消""改地址"有啥不一样？那些不也是意外吗？

**林老师：** 区别很关键，我先点一句、后面会展开：取消、改地址，是**计划之内的业务反应**（客户本来就有权取消）；而错误，是某一步**真的执行失败了**（比如查库存发现根本对不上账）。错误事件，是专门给"失败"用的词汇。

> **【术语卡 · 双语协议】**
> - **中文：** 错误事件
> - **英文：** Error Event
> - **记号：** 事件圈里画一个**小闪电 / 折线箭头**。**抛出**用一个**结束错误事件**（粗圈+实心闪电，画在子流程内部）；**接住**用一个**错误边界事件**（贴在子流程边框上）。
> - **大白话：** "报错"和"接错"的一对。子流程里某步发现干不下去了，就**抛**一个带错误码的错误；外面贴着的错误边界事件**接住**它，转去做补救。
> - **例子：** "查库存"发现缺货 → 抛出"not in stock"错误 → 外层接住 → 走补救流程。

**林老师：** 课件分"抛"和"接"两半讲：

- **To throw（抛出）：** 用一个**错误结束事件**，而且——**must have a label with an error code（必须带一个错误码标签）**。比如标签写 `not in stock`。这个码很重要，是后面"对暗号"用的。
- **To catch（接住）：** 在外层活动 / 子流程的边框上贴一个**错误边界事件**：
  - **带标签**：只接**那个错误码**（catch that error code only）。对上暗号才接。
  - **不带标签**：**任何错误都接**（catch any error）。

**安安：** 所以错误码就像"暗号"——抛的时候喊一句 `not in stock`，接的那边如果也写着 `not in stock`，就接住；写别的就不接。不写暗号的，则来者不拒。

**林老师：** 比喻很准。再补一个重点：**错误边界事件永远是中断式的**。因为一旦某步报错，那个活动 / 子流程显然没法正常完成了，必须打断它、转去补救。这里没有"非中断错误"这种说法。

**安安：** 那如果"接住的人"不在同一层呢？比如错误是在很里面的一层子流程里抛出来的。

**林老师：** 这就是课件专门讲的 **Propagation（传播）**，一句话规则：**The nearest parent with a matching boundary event will handle the error——由最近的、带有匹配边界事件的那一层父级来处理这个错误。**

**林老师：** 我用舞台剧讲这个"往上冒泡"。想象戏中戏套了好几层：最里层 D 出错了——

1. 先看 D 自己这一层有没有贴匹配的错误边界事件？有就 D 自己处理，到此为止。
2. 没有，就**往外冒一层**，看包着它的 C 有没有匹配的？有就 C 处理。
3. 还没有，继续往外冒到 B、到 A……**谁先有匹配的暗号，谁就接住、处理。**

**安安：** 所以错误会像气泡一样**一层层往上冒**，直到撞上第一个能接住它的边界事件。

**林老师：** 对。课件那个 **Check stock（查库存）→ not in stock（缺货）** 的例子，就是在某层抛出 `not in stock`，由最近的、贴着 `not in stock` 错误边界事件的那一层父级接住，然后走它的补救路径。

**安安：** 我把这一站和上一站连起来理解：错误事件，其实就是**"错误"这个触发类型**，通过**错误边界事件**贴在活动上接住。它是边界事件家族里专门管"失败"的那个成员。

**林老师：** 串得非常好。这正是为什么我把边界事件放在错误事件前面讲——错误的"接"，本质就是一个边界事件。

**【转场】** 现在我们到了今天分量最重、也最容易被误解的一站。前面讲的都是"事情还在进行中"的反应。可如果事情已经**顺利做完了**，然后才要反悔、要撤销，怎么办？这就是补偿。

## 9. 第六站：补偿 Compensation

**林老师：** 我先把今天最重要的一句话说在前面，这也是**第五个、第六个易混点**的答案：

> **补偿（Compensation）≠ 错误处理（Error handling）。**
> 错误处理：处理"**正在做的时候失败了**"。
> 补偿：处理"**已经成功做完了，但现在需要撤销 / 善后**"。
> 而且——**补偿不是"把前面那个任务删掉"，而是去做一个真实的、反向的善后动作。**

**安安：** 这个我太需要了。回到开场：钱我已经付了、货仓库已经备好甚至发了，我现在取消。系统不可能"假装我没付过钱"对吧？钱得**真的退**回来。

**林老师：** 一针见血。"付款"这个动作**真实发生过**，你不能按个删除键当它没发生。你得做一个**反向动作**——退款。这个反向动作，就叫补偿。

> **【术语卡 · 双语协议】**
> - **中文：** 补偿
> - **英文：** Compensation
> - **记号：** 一个**"倒带"样子的双左三角 ◄◄** 图标。它出现在两个地方：贴在活动边框上的**补偿边界事件**（连着一个补偿处理器），以及用来触发补偿的**补偿抛出事件**。
> - **大白话：** 给一个"已经做完的活动"配一个**专属的撤销/善后程序**。平时不动；一旦被触发，就把这件已完成的事**反向收拾干净**。
> - **例子：** "付款"配"退款"，"发货"配"处理退货"。

**林老师：** 看它怎么画，课件讲了语法（Handling）：

> **【图示 · 用令牌讲】补偿处理器怎么挂**
> 一个活动（比如 **Handle payment 付款**），在它边框上贴一个**补偿边界事件（◄◄）**，用一条**关联线（虚线）**连到一个单独的活动——**补偿处理器（compensation handler）**，比如 **Reimburse（退款）**。

**林老师：** 课件强调两条语法，特别像我们讲文本注释和事件子流程时的味道：

1. **Syntax: compensation handler is connected with an association** —— 补偿处理器用**关联线（虚线）**连，不是顺序流箭头。
2. **Syntax: compensation handler has no sequence flows** —— 补偿处理器**没有**进出的顺序流。它平时**不在**主干道上，不会被令牌正常走到。

**安安：** 这……怎么又是"虚线、没有进出箭头"？跟事件子流程好像。

**林老师：** 你抓到的是 BPMN 一个统一的设计思想：**凡是"平时不在主干道上、靠触发才启动"的东西，都不用顺序流，而用关联或特殊触发来连。** 事件子流程、补偿处理器都是这一类。区别是：事件子流程是**一整段**埋在流程里的处理；补偿处理器是**专门绑定某一个已完成活动**的撤销程序。

**林老师：** 关键句来了——**When the activity is done and then the compensation is triggered, the compensation handler is executed**：只有当那个活动**已经做完**、并且**补偿被触发**，补偿处理器才执行。

**安安：** 所以触发是有条件的：活动**没做过**，就没什么可补偿的；活动**做完了**，补偿才有意义。

**林老师：** 对。那补偿怎么被"触发"？课件讲了 **Triggering compensation**：

- 用一个**补偿抛出事件（◄◄）**来触发。它和它要触发的那个补偿之间，怎么对应上？——**Linking（连线 / 对暗号）**：
  - **If clear from context: fine** —— 如果上下文很清楚（比如就一个补偿目标），不用特别标，没问题。
  - **If ambiguous: give ... the same label** —— 如果有歧义，就给"抛出补偿的事件"和"对应的补偿"**起同一个标签**，靠标签对上号。（和错误事件的"错误码暗号"是一个套路。）
- 还有一条很重要的连带规则：**An un-catched error in a sub-process will also trigger all compensatable activities in that sub-process** —— 如果一个子流程里冒出一个**没被接住的错误**，它会**顺带触发这个子流程里所有可补偿活动的补偿**。也就是说，子流程"整段失败"时，会自动把里面已经做完的事一一回滚善后。

**安安：** 这条很有人情味——整件事黄了，已经做的那些"既成事实"自动一个个被撤销，而不是留一堆烂摊子。

**林老师：** 正是补偿的精神。来看课件的完整例子，把今天好几个记号串起来。

> **【图示 · 用令牌讲】可取消的采购单处理（综合例）**
> 有一个子流程 **Handle purchase order（处理采购单）**，里面主干道是：**Check PO（检查采购单）** → **Handle payment（付款）** → **Fulfill PO（履约/发货）**（从 `PO received` 到 `PO handled`）。
> 其中两个活动各自挂了**补偿处理器**：
> - **Handle payment（付款）** ── 补偿边界 ◄◄ ── **Reimburse（退款）**
> - **Fulfill PO（履约）** ── 补偿边界 ◄◄ ── **Handle goods return（处理退货）**
> 在子流程边框上，还贴了一个**消息边界事件 PO cancel received（收到取消请求）**，从它引出 → 一个**补偿抛出事件 Cancel PO（◄◄，触发补偿）**。

**林老师：** 现在我们把开场那个场景，用这张图完整地走一遍令牌。

**安安：** 来！我下单了，流程进了 `Handle purchase order`，已经走过 Check PO、Handle payment（我钱付了）、正在或已经 Fulfill PO（货在发）。这时候我点"取消"。

**林老师：** 客户的取消消息，被子流程边框上的**消息边界事件 `PO cancel received`** 接住。注意——这是个**中断式边界事件**，所以它先把这个子流程**正在进行的活儿打断**。

**安安：** 然后呢？光打断不够吧，我钱还在它那、货还在路上。

**林老师：** 对，所以边界事件引出的不是"结束"，而是一个**补偿抛出事件 `Cancel PO`**。它一抛，就去触发**所有已经完成的、可补偿的活动**的补偿处理器：

- 你**已经付过款**（Handle payment 做完了）→ 触发它的补偿 **Reimburse（退款）**，钱**真的退**给你。
- 你的货**已经履约/发出**（Fulfill PO 做完了）→ 触发它的补偿 **Handle goods return（处理退货）**，安排把货退回来。
- 而 **Check PO** 那种"检查一下"的动作，本来就没什么需要撤销的，可以不配补偿。

**安安：** 这就完美回答了我开场的问题！系统不是"假装我没买过"，而是**针对每一个已经做完的步骤，跑一个对应的反向善后**——付款→退款，发货→退货。这就是补偿。

**林老师：** 而且你看，**只有"已经做完"的步骤才会被补偿**。假如你取消得早，货还没发，那 `Fulfill PO` 没完成，就不会触发"处理退货"——因为根本没货可退。补偿天生只针对"既成事实"。

**安安：** 那我把补偿和错误处理彻底分清楚：**错误处理**是"我正在做某步，它失败了，我转去补救（往前找出路）"；**补偿**是"我某步明明成功了，但因为后来反悔/整体失败，我要把它反向撤销（往回收拾）"。

**林老师：** 这就是今天**第五个易混点**的标准答案。再把**第六个**钉死一遍：补偿**不是删除前一个任务**，是**建模一个真实的善后/撤销活动**。退款是要走流程、要动账的真实活动，不是把"付款"那个方块从图上擦掉。

**【小结这一站】** 补偿 = 给已完成活动配的反向善后程序，用补偿边界 ◄◄ + 关联线挂上、无进出顺序流，靠补偿抛出事件触发（必要时用同名标签对号），子流程未捕获的错误会连带触发其中所有可补偿活动。它不同于错误处理，也绝不是"删掉前一步"。

## 10. 误区澄清（Misconception Check）

**林老师：** 进练习之前，我要纠一个最大的、贯穿全集的误解。

**安安：** 你说。

**林老师：** 很多人学完今天会觉得："这些高级事件都是画'坏路径'的、画'倒霉事'的。" **这是错的。**

**安安：** 啊？取消、缺货、报错、退款……听上去确实都挺"倒霉"的。

**林老师：** 但请注意——**异常流程，不等于"坏路径"；很多是事先计划好的正常业务反应。**

- **客户取消订单**：这是客户**正当的权利**，是业务**预料之中**要支持的。退款流程是你产品的一部分，不是 bug。
- **改地址**：完全正常的需求，根本不算"出错"。
- 只有像 **缺货、错误事件** 这种，才算真正的"失败/异常"。

**安安：** 所以同样用"高级事件"画出来的东西，背后的业务含义可能是"计划内的服务"，也可能是"真出事了"。不能一看到边界事件、补偿就当成"这流程有毛病"。

**林老师：** 对。判断一段处理是"计划内反应"还是"真异常"，要看**业务语义**，不是看**用了哪个记号**。一个成熟的流程模型，恰恰是把这些"万一"都**大大方方地画出来、安排好**，而不是假装它们不存在。

**安安：** 这句我记下了：**好的流程图不是只画顺利的那条道，而是把"万一"也安排得明明白白。**

## 11. 把六个记号串成一张图（Integrated Recap by Example）

**林老师：** 在做练习前，我用开场那个电商订单，把今天六个站**一次性**串起来，你听听是不是都对上号了。

**安安：** 好，我边听边在脑子里画。

**林老师：**

**安安：** 那好处（b）我猜：如果有一天供应商从 7 家变成 70 家，多实例**不用重画图**，改个数量就行；并行网关得画 70 条支线，根本没法看。

**林老师：** 答得很好。这就是多实例的核心优势：**数量可变、图不爆炸、可读性强**。

### 练习 2：大学作业流程（对应参考答案 5.2）

**林老师：** 题目讲一个大学出作业的流程：课程协调人决定该换作业了 → **老师设计作业** → 请**若干同事评审** → 收齐所有评审 → **据此修改作业** → **发给学生** → 学生（读题、计算、书写）**作答** → 老师**收集并批改** → 学生**拿到成绩**。要求建出**控制流 + 组织视角 + 数据视角**；**学生可以当黑盒（black box）**。

**安安：** 这题我注意到几个点：第一，"请若干同事评审、收齐所有评审"——这又是**多实例**！第二，"学生当黑盒"——就是画成一个**黑盒泳池（black-box pool）**，只跟它收发消息，不画里面。

**林老师：** 非常好。这正是**参考答案 5.2**要点（原件是手写扫描，我按题意和标准解法给你讲）：

- **组织视角**：用**泳道/泳池**区分角色——课程协调人、老师在自己的泳道里；**学生是一个黑盒泳池**，老师"发作业""收答案"是跨池的**消息流**。

### 练习 3：诺贝尔化学奖评选流程（对应参考答案 5.3）

**林老师：** 这题是书上的 4.23：诺贝尔化学奖按月推进——

- **次年 1 月底（题述 2 月为截止节点）**：回收提名表，委员会筛选出约 250–350 个初选候选；
- **3–5 月**：把初选名单送给**专家**评估；
- **6–8 月**：撰写报告，全体委员签字；
- **9 月**：委员会把推荐报告提交给科学院，开两次会讨论；
- **10 月**：科学院**多数表决**选出得主，决定终局、不可上诉，随后**公布**；

**安安：** 这题最大的特征是**时间**——它整个就是按月份推进的。这里是不是该用**定时器**？

**林老师：** 你点到了**参考答案 5.3**的关键。标准解法里：

## 13. 本集回顾：每个记号回答哪个建模问题（Recap）

**林老师：** 收尾。我把今天六个记号，按"它回答的那个问题"再串一遍。你听一个，自己脑补一个记号。

**安安：** 来，考我。

**林老师：**
1. **"要不要现在就全停？"** → **终止结束事件 Terminate End Event**（实心黑点）。清一层所有令牌、给负面结局、**省着用**。对比普通结束：清一颗 vs 清一层。
2. **"流程期间随时可能冒出来的事，谁来接？"** → **事件子流程 Event Sub-Process**（流程内、虚线框、无进出箭头、靠触发）。实线圈中断、虚线圈非中断。
3. **"怎么给图加说明又不改执行？"** → **文本注释 Text Annotation**（虚线关联）。令牌不经过，只给人看。
4. **"某个活动正在做的时候插一个反应？"** → **边界事件 Boundary Event**（贴在活动边框）。实线打断、虚线不打断；类型有消息、定时器、错误、信号、补偿。和事件子流程的区别：贴一个活动 vs 管整段流程。
5. **"这一步真的失败了怎么办？"** → **错误事件 Error Event**（闪电）。抛出带错误码、由最近的匹配错误边界事件接住、错误会逐层往上冒泡；错误边界永远中断式。
6. **"已经做完的事要反悔/善后怎么办？"** → **补偿 Compensation**（倒带 ◄◄）。给已完成活动配反向善后程序，关联线挂、无顺序流、靠补偿抛出事件触发；**它不是错误处理，也不是删除前一步**。

**安安：** 我再背一遍今天的两条万能口诀：第一，**实线圈打断、虚线圈不打断**，事件子流程和边界事件通吃。第二，**虚线关联给人看、实线箭头给令牌走**，文本注释、补偿处理器都遵守。

**林老师：** 还有一条价值观口诀别忘了：**异常不等于坏路径——好的流程图，把"万一"也画得明明白白。**

**安安：** 收齐了。舞台剧版我也复述一下：什么时候**叫停整场**（终止）、什么时候**插一段应急桥段**（事件子流程）、某一幕边上**贴个随时打断的提示**（边界事件）、演出**真出岔子**（错误）、谢幕后**返场把演过的倒回去补救**（补偿）、以及在剧本边上**写给读者看的批注**（文本注释）。

**林老师：** 完美闭环。
